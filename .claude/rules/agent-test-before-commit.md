# エージェント動作のテストルール

エージェントのCLI起動方法（フラグ・サブコマンド・引数の組み合わせ）を変更・追加したとき、
**コミット前に実際にそのコマンドを実行して動作を確認すること。**

- `reasonix run "hello"` のような最小の動作確認コマンドを手で打って exit 0 を確認する
- `--help` でフラグ一覧を確認するだけでは不十分。実際に動かせ
- 「既存の設定値（フラグ・引数）をそのまま使うだけの薄いラッパー」だからと実機確認を省略しない。実際にエージェントCLIを起動する新しいコードパスである限り、値の出どころに関わらず実行確認の対象である（PR #140 反省会: `resumeCommand`の値は`agent-defaults.json`に既存だったが、それを使って実際にCLIを起動するコードパス自体は新規だった）
- **新しい値・能力（新agentId・extends・promptDelivery種別追加等）を導入したときは、それを消費しうる既存の起動経路を全て洗い出し、実際に触っていない経路が無いか確認してから完了と報告すること。** 自分が直接変更したコードパスだけを実機確認して終わらせない。新しい値は、自分が変更していない別のコードパス（別の起動関数・別のスクリプト）にもそのまま流れ込みうる。そのコードパスが同じ抽象（ログインシェル経由の起動等）を経由していない独自実装だった場合、そこだけ壊れたまま気づかれずに残る（実障害: PR #170で`extends`によるカスタムエージェント定義を追加し、`resolveAgentConfig()`と`codex exec`単体の実行は確認したが、`gh-maestro-reviewer`役への割り当てを経由するRun Review Manager専用の起動経路（`run-review-manager.js`の`runAgentHeadless`）は生spawnで、ログインシェル抽象を経由していなかったため、pwsh関数エージェントで`ENOENT`即失敗した。ユーザーが実運用で踏むまで検出できなかった）
