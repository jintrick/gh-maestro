# 外部コマンド依存の安全ガードはフェイルクローズにする

安全ガード（危険な操作を止めるためのチェック）が、外部コマンド（`git` 等）の実行結果に依存している場合、その検出自体が失敗した（コマンドが無い、例外を投げた等）ときは、警告して処理を継続するのではなく、`--force` 等の明示的なフラグなしでは中断する。

- 実障害: `scripts/install.js` に追加されたWIPブランチ検出ガードが、`git branch --show-current` の呼び出しを try/catch で囲んでいたが、catch パスが警告ログを出すだけで、その後 `~/.gh-maestro/` への破壊的な書き込み処理にそのまま進んでいた（PR #44 Review Manager指摘）。`git` がPATHに無い等でブランチ検出自体が失敗すると、未マージのfeatureブランチにいてもinstallが素通りし、そのガードが防ごうとしていた事故がそのまま再発する。
- 対策: 検出失敗は「安全と判定できない」ことを意味する。安全と確認できない場合は安全側（中断）に倒す。継続する場合は `--force` 等、呼び出し側の明示的な意思表示を必須にする。

# ガードの名前は、実際に保証している範囲と一致させる

安全ガードやその周辺の変数・関数・ログ文言に、実際には提供していない保証を含意する名前を付けない。名前が含意する範囲と、コードが実際に守っている範囲を一致させる。

- 実障害: `scripts/process-lifecycle.js` の sweep が組み立てる除外リストは、変数名・ログ文言ともに「稼働中ワーカー保護」を名乗っていたが、実際には kill の判断に一切関与せず、後段のログ整理から除外するだけだった。この構築が失敗するバグ（Issue #267）が起きた際、`稼働中ワーカー保護の構築に失敗しました` というエラーを見たオーケストレーターが「稼働中ワーカーが kill されうる」と深刻度を誤判定し、他の未対応バグより優先して着手するという作業順序の誤りを招いた。実際の影響はログのローテーションのみで、調査によって初めて誤りと判明した。
- 対策: 「保護」「検証」「安全」等の語を使う前に、それが守る対象と、守らない対象を言語化する。守らない範囲があるなら名前をその範囲に合わせて狭める（例: 「稼働中ワーカー保護」→「後段の整理処理からの除外対象」）。ログ・エラー文言も同様に扱う。読み手は名前から危険度を推定するため、過大な名前は過大な対応を誘発する。
