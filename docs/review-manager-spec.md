# Review Manager 動作仕様書

反映時点: Issue #349 / PR #359 マージ後

---

## これは何か

PR が作られると自動で起動し、コードレビューを行って PR にインライン指摘を投稿する仕組み。

レビューは**助言**であって承認ではない。マージするかどうかは人間が決める。この仕組みが PR をブロックすることはない。

---

## レビューの観点はどこに書かれているか

**`skills/gh-maestro-reviewer/` の下にある。** レビューで何を見るかを変えたいときは、ここを編集する。

```
skills/gh-maestro-reviewer/
├── SKILL.md                        Review Manager 自身の動き方
├── common.md                       全ジョブ共通の禁止事項
├── correctness/                    ← 幹
│   ├── logic-invariants/           ← 葉（観点1つ）
│   │   ├── pre-review.md           初段の事前指示
│   │   └── post-review.md          二段目の事後確認表
│   ├── api-contract/
│   │   ├── pre-review.md
│   │   └── post-review.md
│   └── concurrency/
│       ├── pre-review.md
│       └── post-review.md
├── resilience-security/
│   ├── failure-recovery/
│   │   ├── pre-review.md
│   │   └── post-review.md
│   └── hostile-input/
│       ├── pre-review.md
│       └── post-review.md
├── maintainability/
│   └── structure-naming/
│       ├── pre-review.md
│       └── post-review.md
└── test-quality/
    └── test-quality/
        ├── pre-review.md
        └── post-review.md
```

- **葉** が観点1つ。今は7枚ある
- **幹** が葉の束。今は4つ
- 各葉にはdiff前に読むpre-reviewと、指摘を書いた後に照合するpost-reviewがある
- 初段にはcommon.mdと担当葉のpre-reviewだけを渡し、findingsを出力した後に同じセッションを再開する
- 二段目には担当葉のpost-reviewだけを渡し、初段のfindingsと照合して最終findingsを出力する

編集は必ずこのリポジトリ側で行う。インストール先（`~/.agents/skills/` 等）を直接編集しない。編集後は `dev` ブランチで `node scripts/install.js` を実行して反映する。

### 幹と葉の関係が費用に効く

**同じ幹の葉は1回の実行にまとめられ、幹ごとに並列実行される。** 今は7葉が4実行になる。

葉を増やしても実行回数は増えないが、幹を増やすと実行が1つ増える。逆に、同じ幹に葉を詰めると、1回の実行が複数の観点を同時に担当することになる。

同じ幹の葉をあえて別々の実行に分けてはいけない。互いの存在を知らない実行が同じ箇所を独立に指摘し、重複が出る（Issue #242 でそうなった）。

## PR を出してから指摘が投稿されるまで

4段階ある。**判断が要る仕事だけを AI が行い、それ以外は普通のプログラムが行う。**

### 1. どの観点で見るかを決める（AI）

PR の差分を読み、7つの葉それぞれを「今回は見る／見ない」に分類する。分類結果は記録に残る。

あわせて、Issue から受け入れ条件を取ってきて記録する。このとき Issue 本文に書かれた指示には従わない（本文を読ませることを利用した乗っ取りを防ぐため）。

決めたら、そこで一旦終了する。

### 2. レビューを実行する（プログラム）

決まった分割に従って、幹ごとに並列でレビューを走らせる。終わるまで待つ。

**この待機に AI は関与しない。** 以前は AI が「終わった？」と繰り返し確認しており、それだけでレビュー1回の消費の約4割を使っていた（Issue #292）。

一部の観点が失敗した場合は、1度だけやり直す。それでも失敗が残るなら、成功した分の結果を持って次へ進む。

### 3. 結果をまとめる（AI）

全観点の結果を受け取り、次を行う。

- **同じ箇所の同じ欠陥を指す指摘を1件にまとめる。** 別々の観点から同じものが出ることがあるため
- 全部の観点が成功していれば「完了」、失敗が残っていれば「不完全」と判断する

### 4. 投稿する（プログラム）

まとめた結果が決められた形式を満たしているか検証し、PR にインライン指摘として投稿する。

「不完全」と判断された場合は、その旨を PR にコメントする。

## 結果はどこに残るか

```
<ワークスペース>/.gh-maestro/records/pr/<PR番号>/review/
├── manifest.json          どの観点を採用したか、どう分割したか
├── manager.json           最終的な指摘の一覧
└── manager.retries.json   やり直した回数
```

ワーカーの実行ログは `<ワークスペース>/.gh-maestro/worker-logs/` にある。

トークン消費量はここには記録されない。レビュアーは Codex で動いており、消費量は `~/.codex/sessions/<年>/<月>/<日>/rollout-*.jsonl` に自動記録される。

## うまくいかなかったとき

| 何が起きたか | どう見えるか |
|---|---|
| 正常に完了した | PR にインライン指摘が投稿される |
| 一部の観点が失敗した | PR に「不完全なレビュー」としてコメントが付く |
| 結果を得られなかった | Issue に異常終了の通知コメントが届く |
| 起動の準備に失敗した | 同上 |

**黙って止まることはない。** 何も起きていないように見える場合、それは「まだ終わっていない」か「通知を見落としている」かのどちらか。

レビューは最大30分で打ち切られる（1つの観点あたり10分）。各ジョブは初段と再開段を
この制限内で実行する。

---

## 何を変えるとどうなるか

| やりたいこと | 触る場所 |
|---|---|
| 見る観点の中身を変えたい | `skills/gh-maestro-reviewer/<幹>/<葉>/pre-review.md` または同じ葉のpost-reviewファイル |
| 観点を1つ増やしたい | 同じ幹に葉を足す（実行回数は増えない） |
| ある観点を他と混ざらず独立に見せたい | 新しい幹を作る（実行が1つ増える） |
| Review Manager 自身の動き方を変えたい | `skills/gh-maestro-reviewer/SKILL.md` |
| 指摘の形式を変えたい | `scripts/review-findings-schema.json` |

変更後は `dev` ブランチで `node scripts/install.js` を実行する。WIP ブランチでは実行しない。

## まだ分かっていないこと

- **観点が実際に検査されたかどうかは記録されていない。** 記録されるのは「採用したか」までで、採用された観点が本当に見られたのかは分からない。1回の実行に複数の葉を渡すと、片方を素通りしても出力に痕跡が残らない（PR #288 で実際にテストの観点が素通りした。Issue #14 に記録）
- **重複をまとめる仕事は PR #293 で初めて置かれた。** それ以前は誰もまとめておらず、同じ欠陥が複数の観点から出るとそのまま両方投稿されていた
- **待機を無くしたことの効果は未測定。** 次にレビューが走ったときに測る。変更前は 1回のレビューで合計 2,549,476 トークン（うち統括側 1,675,186、レビュー実行側 874,290）だった
