# architect には論点と参照先だけを渡し、orchestrator が圧縮した事実を渡さない

## 決めたこと

orchestrator は architect の起動プロンプトに「圧縮済み調査コンテクスト」の節を置かない。渡すのは確定済み要件（Issue 本文）と相談したい設計上の論点、および参照先のポインタ（Issue コメント番号、ファイルパス）だけとする。事実の要約・言い換え・評価は書かない。architect は必要な事実を、サブエージェント経由の調査で自分で取りに行く。

この判断は Issue #443 の「orchestrator が工程2で調査して圧縮コンテクストを渡す既存の経路は維持する」という対象外条項を覆す。

## なぜ

Issue #532 の設計相談で、architect が事実でない前提に基づく設計を返した。前提を持ち込んだのは architect ではなく orchestrator である。explorer は実装の事実を正しく報告し、orchestrator がそれを読み替えて圧縮節に確定事実として記載した。architect は与えられた事実が揃っている以上、再検証する理由を持たなかった。

圧縮は、観測された事実と orchestrator の解釈を、受け手が区別できない形で混ぜる。architect には区別する手段がなく、疑う立場にもない。

そして圧縮は情報を足していない。同じ相談で architect は explorer の生の報告コメントを自分で取得して読んでいた。足していたのは解釈だけであり、その解釈が唯一の誤りの入口だった。

## 却下した案

**圧縮節を残し、architect 側に「与えられた事実も再検証せよ」と課す。** 何をどこまで疑うかの判断を architect に負わせることになり、圧縮節の存在価値（読む量を減らす）を打ち消す。誤りの入口を塞がず、検査を1つ増やすだけになる。

**ポインタも渡さず、論点だけにする。** 混入経路は完全に断てるが、architect が探索範囲を手探りすることになり、調査コストと的外れのリスクが上がる。ポインタは「どこを見ればよいか」を示すだけで、解釈を混ぜない。
