# orchestratorも自分の変更をPRで通し、レビュー無しの軽量経路を用意する

## 決めたこと

orchestratorはベースブランチへ直接commit・pushしない。自分の変更もブランチを切りPRにする。あわせて、Review Managerを起動しない軽量なPR経路を用意し、軽い変更をこの経路で通す。軽量経路もアンカーIssueを必須とするが、そのIssueはタイトルだけでよく、本文もassistantの自動起動も伴わない。禁止は配布されるorchestratorスキルの規範として書き、フック・ブランチ保護・CI必須化のいずれも使わない（`docs/adr/0001-no-test-gate-on-push.md`）。

## なぜ

重い側（slow層）のテストはPRに結び付いて実行される。直接コミットした変更はその検証を受けないまま、どの対象プロジェクトでもベースブランチへ入る。実際に、表示形式を変えた直接コミットが重い側の期待値を壊し、それが誰にも見えないまま次に立ったPRで初めて赤として現れた（Issue #475、Issue #487）。

これまでorchestratorの判断基準は変更の影響範囲とコストだけで測っており、その変更が既存のテストに覆われているかを見ていなかった。覆われているかどうかを人が毎回見積もる基準を足しても、見積もりを外した時点で同じことが起きる。変更が常にPRを通れば、覆われているかどうかを判断する必要がなくなる。

PRを通すコストは、Review Managerを起動しない経路を用意することで下げる。`poll-pr.js --no-review-manager` はslow層の起動もテスト申告も抑止しないため、レビューだけを外して検証は残せる。

## 却下した案

- pre-commit／pre-push、ブランチ保護、CI必須化で直接コミットを機械的に禁じる案。停止の判断を機構へ移すことになり、`docs/adr/0001-no-test-gate-on-push.md` に反するため採らなかった。
- 直接コミットを許したまま、その後に `run-slow-tests.js` を人手で回す運用にする案。実行が人の記憶に依存し、回し忘れた時点で検証漏れが同じ構造で再発するため採らなかった。
- 「テストに覆われているコードを触るなら直接コミットしない」という条件を判断基準へ足す案。覆われているかどうかの見積もりを外すと元の事故がそのまま再現するため採らなかった。
- アンカーIssueを要さない軽量経路を新設する案。`push-and-declare.js` はブランチ名のIssue番号でPRとテスト申告を結び付けており、これを切り離すと申告が対象commitへ結び付く仕組み（`docs/adr/0019-convergent-push-and-test-declaration.md`）を弱めるため採らなかった。
- ドキュメントのみの変更を例外として直接コミット可にする案。`push-and-declare.js` がドキュメントのみの変更ではテスト成果物の要求を免除するため、例外を設けなくても軽量経路で通せる。例外の線引きを増やす理由がなく採らなかった。
