# ADRの3条件をオーケストレーターSKILL.mdの本文に置き、機械的に強制しない

## 決めたこと

ADR（`docs/adr/`）を書くかどうかの判定に使う部分——いつ書くか、ADRにする3条件、「却下した案」を作文しない旨、遵守の限界、3条件を満たさない判断の行き先——を `skills/gh-maestro-orchestrator/SKILL.md` の本文に置き、別ファイルへの参照にしない。書くと決めた後にだけ要る部分——書式と見出し、採番、既存ADRを覆したときの扱い——は同スキルのアセット `skills/gh-maestro-orchestrator/adr.md` に置き、3条件を満たすと判定してから開く。

3条件を満たすかどうかを機械的に検証・強制する仕組みは作らない。判定が推論であること、したがって遵守を保証する手段が無いことを、3条件と同じ場所に明記する（Issue #421）。

## なぜ

Issue #419 で入ったのは参照だけだった。工程2で `docs/adr/` を確認する手順はあるが、書き方はどこにも書かれていない。定義が無いため、次に判断が決まってもADRは書かれない。今ある本数はすべて #419 のセッション中の記憶だけで書かれており、そのセッションが終わった時点で書く手段は失われていた。

書くのはorchestratorだけなので、置き場所はorchestratorのスキルになる。`AGENTS.md` に置けばcoderやexplorerにも毎セッション読ませることになるが、彼らはADRを書かない。

判定に使う部分と書式を分けたのは、必要になる瞬間が違うからである。3条件は判断が決まったその瞬間に照合するものであり、そのとき開かれていないファイルは無いのと同じである。書式・採番・改訂の扱いは、書くと決まった後にしか要らない。これは `skills/gh-maestro-orchestrator/triage.md` や `skills/gh-maestro-orchestrator/retrospective.md` と同じ流儀で、SKILL.md に契機を置き、手順をアセットへ逃がす。

3条件の判定そのものは推論である。「覆すコストが大きいか」「読み手がなぜと思うか」「実際に選択肢があったか」を機械が判定する方法は無い。実害も出ている——#419の末尾で追加した3本のうち1本は3条件を満たしておらず、条件を満たすように見せるため存在しない対案を「却下した案」に書いていた。形式を検査する仕組みがあっても、この作文は通っていた。したがって担保になるのは、判断が決まったその場で3条件が文脈にあることだけである。

## 却下した案

- 3条件も書式や採番と一緒にアセットへ切り出す案。照合は判断が決まった瞬間に起こり、そのとき開かれていないファイルは無いのと同じであるため採らなかった。切り出したのは判定後にだけ要る部分に限る。
- 3条件の充足を検査・強制する仕組み（テスト・フック）を作る案。推論を機械が判定できず、条件を通したように見せる形式合わせを誘発するだけであるため採らなかった。作文された対案を検出できないことは #419 で実証されている。
- 定義を `AGENTS.md` に置く案。ADRを書かないcoder・explorerにも毎セッション読ませることになるため採らなかった。
