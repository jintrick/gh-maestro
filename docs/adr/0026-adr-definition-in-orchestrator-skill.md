# ADRの書き方をオーケストレーターSKILL.mdの本文に置き、機械的に強制しない

## 決めたこと

ADR（`docs/adr/`）の書き方——いつ書くか、ADRにする3条件、書式と見出し、採番、既存ADRを覆したときの扱い、3条件を満たさない判断の行き先——を `skills/gh-maestro-orchestrator/SKILL.md` の本文に置く。3条件と「却下した案を作文しない」旨は別ファイルへの参照にしない。

3条件を満たすかどうかを機械的に検証・強制する仕組みは作らない。判定が推論であること、したがって遵守を保証する手段が無いことを、定義と同じ場所に明記する（Issue #421）。

## なぜ

Issue #419 で入ったのは参照だけだった。工程2で `docs/adr/` を確認する手順はあるが、書き方はどこにも書かれていない。定義が無いため、次に判断が決まってもADRは書かれない。今ある本数はすべて #419 のセッション中の記憶だけで書かれており、そのセッションが終わった時点で書く手段は失われていた。

書くのはorchestratorだけなので、置き場所はorchestratorのSKILL.mdになる。`AGENTS.md` に置けばcoderやexplorerにも毎セッション読ませることになるが、彼らはADRを書かない。

3条件の判定は推論である。「覆すコストが大きいか」「読み手がなぜと思うか」「実際に選択肢があったか」を機械が判定する方法は無い。実害も出ている——#419の末尾で追加した3本のうち1本は3条件を満たしておらず、条件を満たすように見せるため存在しない対案を「却下した案」に書いていた。形式を検査する仕組みがあっても、この作文は通っていた。したがって担保になるのは、判断が決まったその場で定義が文脈にあることだけであり、3条件は参照ではなく本文に置く。

## 却下した案

- 3条件を書式や採番と一緒に別ファイル（スキルのアセット）へ切り出す案。書式や採番は書く直前にだけ必要だが、3条件は判断が決まった瞬間に照合するものであり、そのとき開かれていないファイルは無いのと同じであるため採らなかった。
- 3条件の充足を検査・強制する仕組み（テスト・フック）を作る案。推論を機械が判定できず、条件を通したように見せる形式合わせを誘発するだけであるため採らなかった。作文された対案を検出できないことは #419 で実証されている。
- 定義を `AGENTS.md` に置く案。ADRを書かないcoder・explorerにも毎セッション読ませることになるため採らなかった。
