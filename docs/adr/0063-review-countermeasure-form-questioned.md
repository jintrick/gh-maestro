# レビュー指摘への対策が今の形を前提にしていないかは、トリアージで orchestrator が問い、材料は既にある調査から取る

## 決めたこと

工程7のトリアージで、推奨が修正依頼か保留で、指摘が自前の汎用的な仕組みやセキュリティに関わる仕組みを突いている、または同じ仕組みへの指摘が続いているとき、orchestrator は4つの問い（突いている仕組み／代わりになる標準の手段／対策の比較／推奨）に答え、トリアージの表を出す前に Issue コメントへ投稿する。材料は、指摘の本文と、同じ Issue の工程1・工程5の確認コメントから取る。どちらのコメントにも無い仕組みを指摘が突くときだけ、explorer に自前の部分と標準の手段を調べさせる。問いの定義は `skills/gh-maestro-orchestrator/premise-check.md` に置く（#771）。

## なぜ

指摘への対策を検討する場面では、指摘の方向どおりに直すか、標準の形に置き換えるか、というトレードオフが表れることがある（#760）。それでも orchestrator は、今の形を前提に指摘の方向どおりの修正を重ねていた。指摘は Review Manager がコードを読んで書いたもので、突いている箇所を持っている。指摘が突く仕組みの多くはこの PR の計画で作った・触ったもので、工程1・工程5で標準の手段を出典付きで調べ済みである。そのため、トリアージのたびに調査を起こさなくても問いに答えられる。

## 却下した案

- 対象の指摘があるたびに、トリアージの前に explorer へ自前の部分・標準の手段・2つの対策の影響範囲を調べさせる案。材料が揃って見えるが、影響範囲の調査は反省会の役割であり、標準の手段は工程1・工程5で調べ済みのことが多く、調査の重複でトリアージを遅らせるため採らない。
- 工程1・工程5の問いをそのまま工程7でも使う案。工程1は課題、工程5は計画の手段を問い、工程7は指摘への対策を問うため、同じ問いでは対策どうしの比較を問えないため採らない。
- 問いへの答えをレビュースレッドへ書く案。答えは人間が決める前の検討材料で、スレッドには人間が決めた後に決定と理由を書く（ADR 0062）ため採らない。答えのコメントへのリンクを決定の返信に添えて辿れるようにする。
