# 人間への通知は、問いで終わる応答に Stop hook で送る

## 決めたこと

orchestrator から人間への通知（`notify-human.js`）は、orchestrator 自身の操作に任せず、Claude Code の Stop hook で送る。送るのは、`/gh-maestro` を実行したセッションで、応答の最後が問いで終わったときだけとする。セッションの見分けは新しい hook を足さず、既存のセッション初期化でセッションIDを記録して行う（Issue #611、PR #612）。

## なぜ

通知を SKILL.md の規範として orchestrator に実行させていたところ、規範は読み込まれていても発言の瞬間に想起されず、判断や承認を求めたのに一度も通知されないセッションが起きた（Issue #611）。規範を書き足しても同じことが起きるため、モデルの記憶に頼らない仕組みにした。

応答の終わりに毎回送ると、ワーカーの停止通知に反応しただけのターンなど、人間に用の無いターンでも鳴り、通知が無視されるものになる。判断や承認を求める発言は末尾に問いを1つ置く規範（`docs/adr/0007-one-question-per-human-message.md`）があるため、末尾が問いかどうかで人間に用があるかを機械的に見分けられる。

## 却下した案

- 応答が終わるたびに必ず通知する案。用の無いターンでも鳴り、通知の意味が薄れるため採らなかった。
- Notification hook の idle_prompt で送る案。どのターンも終われば入力待ちになるため、鳴る時機が遅れるだけで毎回鳴る点は変わらず、受信監視の稼働中に発火するかも資料から確認できなかったため採らなかった。
- 人間の発言ごとに UserPromptSubmit hook で規範の要約を文脈へ差し込み、通知を含む発言ごとの規範を想起させる案。発言のたびに同じ文をコンテクストへ積み増す浪費になるとして人間が却下した。
- orchestrator セッションの記録用に `/gh-maestro` の UserPromptExpansion へ新しい hook を足す案。同じ契機で動く既存のセッション初期化 hook があり、二重になるため採らなかった。
