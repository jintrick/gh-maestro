# レビュアーはテストを一切実行しない

## 決めたこと

Review Manager とレビュージョブは、テストを実行しない。スコープ限定なしの全件実行だけでなく、差分で変わったテストファイルに絞った実行も含む。全体ビルドも実行しない。テストが通るかどうかは、コーダーの申告と slow 層の実行結果で確かめる。レビューはコードとテストを読んで判断する。

slow テスト1件20秒の上限（`docs/adr/0049-slow-test-20s-per-test-limit.md`）は、コーダーの手順で守らせる。レビュアーは時間を測らない。レビュアーに残るのは、テスト関数が正しい層に置かれているかを読んで判断する部分である。

## なぜ

2026-11-18、Issue #791 で、GijiAI PR #573 のレビュー1回（指摘0件、約5分）が Codex の5時間枠を13pt消費した原因を調べた。4本のジョブのうち3本が同じテストをそれぞれ実行し、その出力をコンテキストに読み込んでいた。

テストが通るかどうかは、コーダーの申告と slow 層の結果で既に分かっている。レビューで流し直しても新しい事実は得られない。レビュー用の作業場での再実行は環境差を持ち込み、申告と食い違えばどちらを信じるかという問題を生む。実行者が結果を申告し、確認する側は申告の存在・古さを見るという分担（AGENTS.md「停止を自動機構に委ねない」、`docs/adr/0001-no-test-gate-on-push.md`）にも反する。テストを壊して落ちるかを確かめる変異確認もコーダーの役目である（`docs/adr/0060-mutation-check-scope-limited.md`）。

## 却下した案

- **差分で変わったテストファイルに絞ったピンポイント実行は許す案**: Issue #196 / PR #198（2026-07-30）で全件実行を禁じたときから続いていた規範である。#196 の問題は全件実行の巨大な出力であり、絞った実行を許す理由は記録に無い。当時の調査ワーカーはテスト実行とビルドの全面禁止を、architect の最初の設計案はレビューワーカーにコマンドを実行させない形を提案していた。絞っても上記の理由はどれも解消しないため採らない。
- **slow テストの20秒上限を確かめるためだけに、レビュアーにテスト1件の単独実行を残す案**: 0049 は上限をレビューのテスト品質観点でも守らせるとしていた。しかし上限はコーダーの手順で守らせられ、例外を残せば「確認のためなら流してよい」という経路が戻るため採らない。
