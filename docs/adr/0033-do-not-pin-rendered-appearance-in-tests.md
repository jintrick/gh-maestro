# 画面表示の見た目をテストで固定しない

## 決めたこと

監視ペインのように人間が目で見て判断する出力について、描画された文字列の見た目をテストで固定しない。区切り記号、バーの本数、空白の詰め方、時間の書式、見出しの文言は検証しない。

検証するのは、画面を見ても分からないものだけとする。行数（1ワーカーが1行に畳まれているか）、識別子（どのワーカーか、PIDは何か）、状態（停止しているものが停止として出ているか）、幅に収まること、大小関係（長い区間ほどバーが長いこと）である。

## なぜ

見た目が正しいかどうかを判断できるのは人間であり、テストではない。表示を1文字単位で固定すると、見た目を変えるたびに必ずテストが落ちる。Issue #471 の作業中、区切りを変え、時間の書式を変え、見出しを戻し、合計時間を1行目へ移すたびにテストを直した。1回の表示変更につき数件から十数件である。表示は人間の要望で頻繁に変わるため、この費用は繰り返し発生する。

一方、テストでなければ守れないものもある。停止したプロセスが「動いている」と表示される欠陥（Issue #467）は、画面を見ても分からない。緑の丸が出ていることと、そのプロセスが生きていることは別である。同じワーカーが複数行に増える欠陥も、行が増えていることには気づけても、それが同一ワーカーかどうかは画面からは判別できない。

この2つを分けて、後者だけをテストで守る。

## 却下した案

- 見た目も含めて固定し、表示を変えるときはテストも一緒に直す案。実際にそう運用していたが、変更のたびに落ちるテストが開発を止めるため、人間の判断で採らなかった。
- 表示に関するテストをすべて削除する案。停止判定や畳み込みの回帰を検出できなくなる。これらは画面を見ても分からないため、人間による確認では代替できない。
- 描画結果をスナップショットとして保存し、差分が出たら人間が承認する案。承認の手間が毎回発生し、承認を惰性で通す運用に落ちるため採らなかった。
