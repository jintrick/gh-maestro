# ADRの作成は、規範への参照行の書き込みと同じ操作で行う

## 決めたこと

ADR の作成は、規範文書への参照行の書き込みを含む単一の操作とする。参照行が無いことを検査して拒否するだけの経路にしない。呼び出し側が規範文書を手で編集してから作成スクリプトを呼ぶ形を、正規の手順として残さない。

## なぜ

Issue #534 が名指しした問題は、ADR が規範文に結び付かないまま作られ、決定がワーカーへ届かないことだった。ワーカーは `docs/adr/` を読まない設計であり、参照行が無ければ決定は誰にも届かない。そして根本は、参照行を置くかどうかが orchestrator の推論に委ねられていて素通りされることにあった。

実装された対策は検査と拒否だけで、参照行を書く行為は推論に委ねられたまま残った。宙に浮いた ADR は作れなくなったが、書く側の確実性は上がっていない。

さらに、規範文書の編集は本来 Issue アンカー付きの PR 経路を通す。検査だけの経路は呼び出し側に、ADR を1本書くたびに PR を1本立てるか、経路を通さず規範を編集するかの二択を強いる。Issue #536 の作業中に orchestrator が後者を選び、工程4へ越権編集した。

書き込みを同じ操作に含めれば、素通りも越権も構造的に起こらない。

## 却下した案

**検査と拒否だけを残し、参照行は呼び出し側が書く（現状）。** 決定的なスクリプトを入口にした目的が、欠落の検出までで止まる。書く行為が推論に残る限り、`docs/adr/0034` と `0037` で起きた素通りは再発しうる。加えて、規範文書の手編集を正規手順に組み込むため、経路違反を誘発する。

**参照行を規範文書に置かず、ADR の front matter だけで結び付ける。** 参照を1箇所にまとめられるが、ワーカーは `docs/adr/` を読まないため決定が届かない。これは Issue #534 の既決事項で既に却下されている。
