# 修正 push の後にレビューし直すかは orchestrator が判断して決める

## 決めたこと

修正 push の後に Review Manager でレビューし直すかどうかは、orchestrator が push ごとに判断して決める。選択肢は、新しい HEAD をレビューし直させる、転送済みの指摘について explorer に事実確認だけさせる、どちらもしない、の3つである。判断の目安は手順書に置くが、件数などの機械的な条件にはしない。人間へは事前に尋ねず、マージ判断の提示で選んだものと理由を示す。何も渡さない起動（初回のレビュー、PR 検出時の自動起動）の Review Manager の動作・読むファイル・規範は変えない（Issue #717）。

## なぜ

これまでは修正 push の後に Review Manager を再実行せず、転送済みの BLOCKER/MAJOR を explorer が事実確認するだけだった。そのため、修正で入った変更そのものは誰もレビューしなかった。モデルを潤沢に使えるようになり、レビューし直す費用を払えるようになった。一方、修正の大半は指摘箇所だけの局所的なものであり、毎回全体をレビューし直すのは見合わない。修正がどこまで広がったかを見て判断できるのは、トリアージから修正依頼までを持っている orchestrator である。ワーカーの起動と再試行の判断を orchestrator が持つ方針（docs/adr/0006-no-headless-agent-retry.md）にも沿う。初回のレビューを変えないのは、再レビューのための追加が、すべての PR が通るレビュー本線の品質に波及しないようにするためである（人間の指示）。

## 却下した案

- 修正 push の後はレビューし直さない（従来の運用）。費用は小さいが、修正で入った変更が未レビューのままマージ候補になる。モデルの割り当てに余裕が無くなったときに、再びこちらへ戻す案として合理的に見えうる。
- 修正 push のたびに必ずレビューし直す。orchestrator が最初に出した案で、規則としては単純で判断の揺れが無い。局所的な修正にも全体のレビュー費用がかかり、新しい指摘が続いて終わらなくなりやすいため、人間が orchestrator の判断に委ねる形を選んだ。
