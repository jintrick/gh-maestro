# 人間への通知は、orchestrator の応答が終わってから少し遅らせて送り、その間に次の応答終了か人間の入力があれば取り消す

## 決めたこと

orchestrator から人間への通知（`notify-human.js`）は、Claude Code の hook で送る。`/gh-maestro` を実行したセッションで応答が終わったら（Stop hook）、すぐには送らず、60秒後の送信を予約する。予約が既にあれば、それを取り消して予約し直す。人間が入力したら（UserPromptSubmit hook）、予約を取り消す。60秒のあいだにどちらも起きなければ、通知を1回送る。応答の内容（末尾が問いかどうか等）で送るかどうかを判定しない。ただし、応答の文章が目印「—」（U+2014 の1文字）と完全に一致するターンは、orchestrator が「人間に用が無い」と宣言したものとして扱い、予約しない。既にある予約も置き換えず、取り消さない。目印を付けるのは orchestrator であり、hook は一致を見るだけで、人間に用があるかを推測しない。セッションの見分けは、既存のセッション初期化で記録したセッションIDで行う（Issue #611、#615）。

## なぜ

hook が見られるのは応答の形だけであり、人間に用があるかどうかは判定できない。人間に知らせるべき応答は、判断や承認を求める問いだけではない。作業の完了や結果の報告も含まれ、それらは問いで終わるとは限らない。形で絞ると、知らせるべき応答が黙って落ちる。また、問いで終えることを通知の条件にすると、通知されるかどうかが再び orchestrator が規範を思い出せるかに依存する。Stop hook に移したのは、その依存（Issue #611）をなくすためだった。

一方、応答が終わるたびにすぐ送ると、監視やワーカーの通知に反応しただけのターンでも鳴る。実際に、人間へ問いを出した直後に届いた監視の通知へ orchestrator が反応し、通知が重なった。遅らせて次の応答終了で取り消せば、立て続けの動きは静かになった後の1回にまとまる。通知の本文はリポジトリ名だけで、どのターンが送っても同じなので、取り消して置き換えても失うものは無い。人間の入力で取り消すのは、入力したということは画面の前にいるからである。

この方式は、orchestrator が人間に用の無いことを喋らないことを前提にする。喋らなかったターンでも Stop hook は発火して予約を置き換えるだけなので、通知の回数は増えないが、チャットに余計な発言が残れば人間はそれを読む手間を負う。

目印を置いたのは、監視の通知に一言反応しただけのターンでも、その後60秒静かなら通知が届いてしまったためである。人間は「そんな報告はいらない」として、この雑音を拒んだ。人間に用があるかを知っているのは orchestrator だけなので、判断は orchestrator が目印で示し、届けることは hook が受け持つ。目印を付け忘れたときに起きるのは余分な通知1回だけで、必要な通知が落ちる方向には失敗しない。目印のターンが既存の予約に触れないのは、人間へ問いを出した直後の監視の通知に「—」で反応したとき、問いの通知を消さないためである。

## 却下した案

- 応答の末尾が問いで終わるときだけ通知する案（`docs/adr/0044-notify-human-by-stop-hook-on-question.md`）。hook には人間に用があるかを判定できず、問いで終わらない完了報告などが通知されない。問いで終える規範を守れるかに通知が依存し、Stop hook に移した目的と矛盾するとして人間が破棄した。
- 応答が終わるたびにすぐ通知する案。監視の通知に反応しただけのターンでも鳴り、人間が「通知がうるさくて仕方がない」として採らなかった。
- 通知をすぐ送り、その後一定時間は送らない案（クールダウン）。人間とのやり取りの最中でも一定時間が空くたびに鳴り、不在中に動きが続くと繰り返し鳴るため採らなかった。
- 応答の文章が空なら通知しない案（`last_assistant_message` または transcript で判定する）。文章を出さずに終えたターンで `last_assistant_message` が空になるかを資料で確かめられず、遅延と取り消しで同じ目的を果たせるため採らなかった。
- orchestrator が「人間に用がある」ときだけ目印を付け、付いた応答だけを通知する案（オプトイン）。付け忘れると必要な通知が落ち、通知が orchestrator の想起に依存する問題（Issue #611）が戻るため採らなかった。目印は「用が無い」側に付ける。
- Notification hook の idle_prompt で送る案。鳴る時機が遅れ、受信監視の稼働中に発火するかも資料から確認できなかったため採らなかった。
- 人間の発言ごとに UserPromptSubmit hook で規範の要約を文脈へ差し込み、通知を含む発言ごとの規範を想起させる案。発言のたびに同じ文をコンテクストへ積み増す浪費になるとして人間が却下した。予約の取り消しに使う UserPromptSubmit hook は文脈へ何も出力しないので、これとは別である。
- orchestrator セッションの記録用に `/gh-maestro` の UserPromptExpansion へ新しい hook を足す案。同じ契機で動く既存のセッション初期化 hook があり、二重になるため採らなかった。
