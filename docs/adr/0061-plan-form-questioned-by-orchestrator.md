# 計画が今の形を前提にしていないかは、計画を評価する orchestrator が問い、コーダーの計画の書式は変えない

## 決めたこと

工程5で、計画が自前の汎用的な仕組みやセキュリティに関わる仕組みを作る、または残すとき、それを標準の手段と比べる問いには orchestrator が答える。材料は計画の本文と、既存パターンの照合と同じ依頼で explorer が集めた事実である。コーダーの計画の書式には、案の比較やトレードオフの欄を足さない。問いの定義は `skills/gh-maestro-orchestrator/premise-check.md` に置く（#766）。

## なぜ

コーダーは受け入れ条件を満たす計画を書くだけで、案を比べることはしない。gh-maestro と gijiai の直近の計画を確かめても、トレードオフを論じた計画はほぼ無かった。gijiai では、プロジェクトの規範で計画に「採用する既存の手段」と「自前で作る箇所とその理由」を書かせていた。それでも #517 では、ライブラリを部品として使い、残りを自前で並べる計画が承認され、その後の手直しの末に作り直しになった。書かせた欄は、規範を守った証拠として働いただけで、形を疑う役には立たなかった。形を疑うには、計画を書いた者とは別の者が、計画の外にある標準の形と比べる必要がある。

## 却下した案

- コーダーの計画の書式に、採用する既存の手段や自前で作る理由、案の比較の欄を足す案。計画の中で完結するので手軽に見えるが、gijiai #517 で実際に行われ、欄が埋まったまま形が疑われなかったため採らない。
- 工程1の4段の問い（今の形／標準の形／標準に戻した場合／要求の成否）をそのまま工程5でも使う案。工程1は課題について問い、工程5は計画の手段について問うため、同じ問いでは答えが重ならず、工程5で捕まえたいもの（ライブラリを部品としてだけ使う形）を問えないため採らない。
