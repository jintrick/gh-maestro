# slow テストはテスト関数1件を単独で20秒以内に収め、収まらないものは廃止して必要なときだけ実機確認する

## 決めたこと

slow 層のテストは、テスト関数1件を単独で実行して20秒以内に終わらなければならない。20秒を超えるテストを作ってはならない。

既に20秒を超えているテストは、まず待ち時間・ポーリング間隔・タイムアウト値の注入などで速くできないかを試す。できなければ廃止し、そのテストが確かめていたことを実機確認の手順として残す。実機確認は、その領域の変更で本当に必要なときだけ行い、通常の変更では行わない。毎回走るテストとは切り離す。

この上限は commit・push・merge を機械的に止める検査にはしない（`docs/adr/0001-no-test-gate-on-push.md`）。コーダーの手順とレビューのテスト品質観点で守らせる。

## なぜ

2026-10-30、Issue #662 / PR #663 で、slow 層（37ファイル・約258件）の1回の実行が12分を超えて終わらず、人間が停止した。通常の実行でも、失敗したテスト1件がタイムアウトまで48秒待っていた。テストは機能を変更するたびに増え続けており、1件ごとの重さに上限が無い限り、全体の実行時間は増える一方になる。slow 層は PR の HEAD ごとに走り、結果が揃うまでマージ判断を出せないため、その時間はそのまま開発の待ち時間になる。

重いテストの多くは、ほとんどの変更では確かめる必要のない経路（常駐プロセスの実起動、実時間の待機など）を毎回確かめている。その経路を本当に確かめる必要があるのは、その領域を変えたときだけである。

## 却下した案

- slow 層全体の実行時間に上限（最悪でも3〜5分）を設ける案。人間が最初に示した基準だが、テストが変更のたびに増えるため、全体の上限は1件ずつの追加では破られたことに気付けず、気付いたときには既に超えている。新しいテストを書く時点で判断できるのは1件ごとの上限であるため、テスト関数単位の上限を採った。
- 20秒を超えるテストも、毎回走る slow 層に残し続ける案。今回の状態そのものであり、ほとんどの変更で不要な確認のために毎回待つことになるため採らなかった。
