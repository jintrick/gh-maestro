# テスト層の分類基準はコーダースキルとレビュー観点に置き、rules と機械検査には置かない

## 決めたこと

テスト関数を毎回側と分離側のどちらへ置くかの基準は、`skills/_partials/coder-workflow.md`（全エージェントのコーダーへ配布される）と、`skills/gh-maestro-reviewer/test-quality/test-quality/post-review.md`（テスト品質の観点）の2箇所に置く。基準の文言そのものは `config.json` の宣言に持たせない。

あわせて `.claude/rules/test-layer-split.md` を削除する。

分類の単位はテスト関数とし、テストファイルとしない。

## なぜ

Issue #452 は分離基準を正しく定めたが、置き場所が `.claude/rules/` だった。rules はファイルを開いたときに文脈へ流し込まれる補助であり、そこに置いた基準は Claude Code にしか届かない。gh-maestro は codex や agy をコーダーに選べるため、エージェントによって基準が違う状態になっていた。しかも `paths` が `scripts/**` と `tests/**` で、このリポジトリでは実質すべての作業に一致する。全マッチのルールは `AGENTS.md` に書くのと同じ効果しか持たず、ファイルを読むたびに繰り返し流し込まれる分だけ悪い。

基準を `config.json` の宣言に載せる案も検討したが、宣言に載せるべきはプロジェクトごとに変わる値（層名・実行コマンド・対象ファイル・時間の目標）である。「重い起動を伴うか、実際に待つか」は値ではなく判断の物差しであり、どのプロジェクトでも変わらない。設定に置いても全プロジェクトで同じ文字列が並ぶだけになる。

分類の単位をテスト関数と明記するのは、Issue #452 / PR #453 がファイル単位で振り分けた結果、遅くない1240関数が「同じファイルに遅い関数がある」という理由だけで毎回のテストから外れたためである（Issue #459）。毎回側に残っていたのは983関数で、全体2434関数の4割だった。単位を明記しなければ同じことが再発する。

## 却下した案

- 毎回側のテストを静的に検査し、実プロセス起動や待機を含むものがあれば落とす案。コーダーが間違えても必ず止まる強制力があるが、検査の実装と維持が要る。人間の判断で、まず文書とレビューの二本立てで運用し、破られ続けるようなら機械化を検討することにした。
- 毎回側の実行中だけ実プロセス起動と待機を禁止し、呼ばれたら例外にする案。同上の理由で採らなかった。加えて、テストの実行環境に禁止機構を差し込むこと自体が、テストの隔離構造（`docs/adr/0017-isolate-worker-environment-from-tests.md`）に干渉する。
- 基準を `config.json` の宣言に持たせる案。上記のとおり、可変な値ではなく不変な物差しであるため採らなかった。宣言側に残すのは、プロジェクトごとに変わる値だけとする。
- `.claude/rules/test-layer-split.md` を残したまま、コーダースキルにも同じ基準を書く案。正本が2つになり、片方だけが更新される状態を作るため採らなかった。
