# プロセスの生死は PID ではなく、死ねば OS が解放するもので判定する

## 決めたこと

プロセスの生死を PID で判定しない。相手が死ねば OS が自動的に解放・通知するもので判定する。親子関係がある相手は、親子間のパイプの切断（子が受け取る stdin の EOF）で判定する。親子関係がない相手は、見張られる側が名前付きパイプ（Windows）／Unix domain socket（他 OS）を保持し、見張る側がそこへ接続できるかで判定する。どちらも広く使われている標準的な手法であり、独自のプロトコルは作らない。

生存確認の手続きは共通のモジュール1か所にまとめ、各常駐・スクリプトが個別に生死を判定しない。PID はプロセスを停止するためだけに残す。

## なぜ

PID は OS に再利用される番号でしかない。PID で生死を判定すると、別プロセスとの取り違えを防ぐために起動時刻の照会を重ねる必要が生じる。Windows ではその照会のたびに PowerShell（と cmd.exe）を起動しており、常駐プロセスが短い間隔で生存確認を繰り返す結果、数分で数百回の起動が発生し、起動のたびに Windows Defender の動作監視と AMSI スキャンを招いていた。人間の観測では Defender が常時およそ 500MB のメモリと 10〜20% の CPU を使っていた（Issue #654）。

生存確認がまとまっておらず、dead-man's switch、PR 監視、worker-supervisor、監視ペインなどが、それぞれ PID の確認と起動時刻の照会を個別に呼んでいた。このため、照会の方式を直すにも全箇所に手を入れる必要があった。

死ねば OS が解放するもので判定すれば、PID 再利用による取り違えは原理的に起きず、照会のための外部プロセスも要らない。

## 却下した案

- 起動時刻の照会結果を PID 単位でキャッシュし、初回だけ照会する案（Issue #654 の最初の設計検討の候補 A）。PID で判定する前提を残したまま照会回数を減らすだけで、見回りの間隔の間に PID が再利用されると常駐が自滅しそこねる。対症療法であるため採らなかった。
- 上の案に、数分ごとの再照会を加えて被害の上限を区切る案。取り違えの被害を時間で区切るだけで、原因は残る。
- ファイルロック（flock、LockFileEx）で生死を判定する案。Node の標準 API には、プロセスの死で解放されるロックがなく、ネイティブ依存を加える必要があるため採らなかった。
