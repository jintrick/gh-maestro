# サイクルの時間計測は決定論的スクリプトの自動記録だけで行う

## 決めたこと

開発サイクルの所要時間計測は、決定論的なスクリプトの実行に伴う自動記録だけで行う。orchestrator が工程番号を名乗る、打刻コマンドを叩くといった、モデルの遵守に依存する記録経路は作らない。

その結果として、計測できる区間は `skills/gh-maestro-orchestrator/SKILL.md` の工程1-13と1対1には対応しない。区間はイベント間のブロック（起票、ワーカー起動、計画報告、承認、PR作成、レビュー完了、マージ、finalize）として粗く取る。

## なぜ

工程1-13の境界の多くは orchestrator の判断の中にしかなく、機械的なイベントを持たない。工程6の一次評価も工程10のトリアージも、外から見れば何も起きていない時間である。工程番号と1対1に対応する計測を得るには、orchestrator に工程遷移のたび打刻を義務づけるしかない。

しかしそれは、計測の土台をモデルの遵守の上に置くことである。打刻を1回飛ばした区間は、短かったのか記録が漏れたのかを事後に区別できない。ボトルネックを探すための道具が、欠損とゼロを取り違えたまま結論を出す。この計測は「時間がかかり過ぎる」という主観を事実に置き換えるために作るのだから、その事実自体が主観的な遵守に依存しては目的を果たさない。

自動記録に限れば区間は粗くなる。だが記録があるかないかは常に確定する。粗いが確実な事実は、細かいが抜けているかもしれない事実より使える。

これは「決定論的な検証と公開は、可能な限りモデルのプロンプトの外に置く」（`AGENTS.md` レビュー方針）と同じ判断を、レビューではなく計測に適用したものである。

## 却下した案

orchestrator が工程に入るたび打刻コマンドを叩く義務を `skills/gh-maestro-orchestrator/SKILL.md` に追加する案。工程1-13と1対1に対応する計測が得られ、既にある「工程番号を名乗る」規約とも相性がよい。人間にこの案を提示した上で、上記の理由により自動記録のみを採った。
