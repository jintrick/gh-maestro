# `dev` の分岐元は `main` / `master` に限定し、既定ブランチを問い合わせない

## 決めたこと

`scripts/gh-maestro-setup.js` の `ensureDevBranch()` は、`dev` の分岐元を次のとおり決める。

- `main` だけが存在する → `main` から作る
- `master` だけが存在する → `master` から作る
- 両方が存在する → `dev` を作らずに停止する
- どちらも存在しない → `dev` を作らずに停止する

リポジトリへ既定ブランチ名を問い合わせて解決する処理は持たない。停止する経路で、現在チェックアウトしているブランチへフォールバックしない。

## なぜ

`dev` はそのプロジェクトの開発の基準になるブランチであり、どこから生えたかを後から見分けるのは難しい。誤った場所から生えても、しばらく誰も気づかない。したがって「分岐元が決められないときに止まる」ことより「誤った分岐元から静かに作られる」ことの方が害が大きい。

`main` と `master` の両方が存在する状態は、意図された構成ではなく事故として扱う。どちらが既定ブランチかを gh-maestro が推測して片方を選ぶと、推測が外れた場合に上の「静かに誤った場所から生える」が起きる。推測しないことで、人間がブランチを整理するまで先へ進まない。

経緯は Issue #530 / PR #531 にある。元の実装は分岐元を `main` に固定しており、既定ブランチが `main` でないプロジェクトでは導入が止まっていた。

## 却下した案

**既定ブランチをリポジトリへ問い合わせて解決する。** `refs/remotes/origin/HEAD` への symbolic ref 問い合わせで解決する案を実装計画まで進めたが、採らなかった。この参照は clone 時に作られるローカルのキャッシュであり、`git init` してから `git remote add` したリポジトリには存在しない。「尋ねたが答えが得られない」という失敗の形を新しく持ち込むことになり、`main` / `master` の存在確認で足りる範囲に対して割に合わない。

**開始点を省略して現在の HEAD から分岐する。** `git checkout -b dev` は開始点を省略すると現在の HEAD から分岐するため、既定ブランチ名を知る必要がなくなり、分岐元の解決に失敗する経路そのものが消える。いったんこの案を採って実装したが、PR #531 のレビューで却下した。既定ブランチ以外をチェックアウトした状態で setup を実行すると、`dev` が未統合の作業内容から生え、以後の基準ブランチが誤った履歴を持つ。`ensureDevBranch()` が作成に入るのはローカルに `dev` が無いときだけなので発生頻度は低いが、起きたときに壊れるものが大きく、かつ誰も気づかない。
