# テストの質は coder の申告を軸にし、Review Manager はその申告を検証する

## 決めたこと

質の低いテストの再生産を防ぐ手段は、Review Manager にテストの質をゼロから判定させることではなく、次の分担にする。

- coder は、テストを書く前に `.claude/rules/test-quality-criteria.md` を読む。追加・書き直したテスト1件ごとに「何が壊れたら失敗するか」「期待値の出所」「入れた欠陥と結果（または実施しない理由）」を PR に申告する。変異確認は、新規・書き直しのテストすべてについて、結果か実施しない理由を必ず書く。
- Review Manager の test-quality 葉は、その申告を実際のテストコードと突き合わせて検証し、基準の条件番号を付けて指摘する。
- 申告の欠落や変異の未実施があっても、commit・push・merge は止めない。事実として示し、判断は orchestrator と人間が持つ。

## なぜ

Issue #669 で、モデルに大量のテストの質を抽象的に判定させると、482件中451件を同じ定型文で「残す」と済ませた。テスト1件ごとに「どの行・どの欠陥・期待値の出所」を具体的に書かせると、判定が中身を持ち、退行を見逃した理由まで特定できた。coder の手作業の変異確認でも、検出力の無いテストが見つかった。

主張を具体的に書かせれば、後段（レビュー・機械の検査）が検証できる対象を持つ。主張が無いまま後段に判定させると、判定は coder の意図（何を検出したいか）を知らず、定型文に流れる。

過去の Test Quality 指摘16件のうち13件は修正または保留へ積まれていた（Issue #671）。指摘の扱いではなく、基準が書き手とレビューに届いていないこと、主張を書かせる仕組みが無いことが欠けていた。

## 却下した案

- **Review Manager にテストの質をゼロから判定させる（当初の人間の案）**: 後追いで、作られる前には防げない。coder の意図が分からないまま判定すると、#669 の最初の判定と同じく定型文になる。単一モデルの判断に依存する。
- **汎用のミューテーションテスト道具（Stryker 等）の導入**: 自動生成される変異は構文上の置換で、基準の言う「何が壊れたら」（仕様上の欠陥）とずれる。約2,700件の full 層と slow 層に掛ける実行コストが大きい。生き残った変異の振り分けが新しいノイズになる。
- **変異確認を受け入れ条件に直結するテストだけに求める**: 負担は軽いが、それ以外のテストが質の低いまま入る経路が残る。#669 では1件あたり数分の負担だった。
- **申告の欠落・変異の未検出で push・merge を止める**: docs/adr/0001-no-test-gate-on-push.md に反する。
- **基準の `paths` を広げる、または AGENTS.md に全文を移す**: 広い `paths` は AGENTS.md と同じ効果しか持たず、Review Manager が動く codex には `.claude/rules` が届かない。必要な手順から明示的に参照する。
