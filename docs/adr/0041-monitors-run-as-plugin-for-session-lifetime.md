# 受信監視とPR監視はプラグインの monitors でセッションの間ずっと動かす

## 決めたこと

orchestrator の受信監視（`msg-poll.js`）とPR監視（`poll-pr.js`）は、Claude Code の Monitor ツールではなく、gh-maestro プラグインの monitors として動かす。monitors は `/gh-maestro` の起動を契機に固定のコマンドで立ち上がり、セッションが終わるまで動き続ける。PR監視は Issue ごとに対象が変わるため、固定の監視役がワークスペースの制御レコードを読み、orchestrator が CLI でその対象を切り替える（Issue #581、PR #582）。

## なぜ

Monitor ツールの期限は最長30分で、延ばす設定は無い（2026-09 時点の公式文書）。orchestrator は30分ごとに2本の監視を張り直しており、その間はワーカーの報告もPRの通知も届かなかった。さらにPR監視が打ち切られると、それが起動していた slow 層の実行とレビュー担当まで止まり、slow 層の予約が「実行中」のまま残って二度と実行されなかった。2026-09-26〜27 に、slow 層の結果が無いまま人間がマージを判断することが2回起きた。プラグインの monitors はセッションの間打ち切られないため、張り直しと巻き込み停止の両方が構造的に起きなくなる。

## 却下した案

- Monitor ツールのまま、30分ごとに orchestrator が張り直す案。実際に運用していたが、張り直しまでの通知の空白と、PR監視の子プロセス（slow 層、レビュー担当）の巻き込み停止を防げなかった。
- Monitor ツールの打ち切りを前提に、slow 層の実行だけを PR 監視から切り離して生き残らせる案（Issue #581 の最初の計画）。打ち切りそのものと受信監視の空白は残り、セッション終了後に孤立したテスト実行を生むため採らなかった。
