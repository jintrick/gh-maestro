# JSON の状態ファイルは書き手を1つに保ち、プロセス間の同期に使わない

## 決めたこと

`workers.json`、`status-pane.json`、`poll-slow-test-<PR>.json` のような JSON の状態ファイルは、状態の記録として使う。複数のプロセスが同じファイルを読んで書き戻す形の同期には使わない。書き手は常に1つに保つ。

ある子プロセスが自分の情報を親の書いた記録へ書き足したくなったら、書き戻す仕組みを足すのではなく、親がその情報を自分で得られる形にするか、その情報を持たずに済む設計へ変える（Issue #471、PR #472）。

## なぜ

JSON は構造化データであり、更新には読み込み・変更・書き戻しの3段が要る。この3段はファイルシステムの上で不可分ではない。プロセスが2つ絡んだ時点で、片方が読んだ後もう片方が書く、という順序が発生する。

Issue #471 では、監視ペインの入れ替わりを確認するためにプロセスIDを記録することにした。ペインの子プロセスが起動直後にレジストリを読み、自分のIDを書き足す実装になった。親がレジストリを書く前に子がそこへ到達すると、子は「記録が無い」と判断して何も書かず、後から親が書く記録にはIDが入らない。起動順序次第で、確認したかった値が恒常的に空になる。

順序に依存しないよう直す修正は実装まで済んでいた。しかしそれは、読んで書き戻す構造を残したまま、今回の経路だけを塞ぐものだった。同種の状態ファイルはこのリポジトリに複数あり、書き戻しを許す前例を作れば各所へ広がる。

ペインの入れ替わりは、記録済みのペイン識別子が変わったかどうかで確認できる。プロセスIDを持たなければ、子が書き戻す必要も、順序を気にする必要も無くなる。

なお、書き手が1つに保たれている限り、状態の記録として JSON を使うこと自体は問題としない。禁じるのは同期の手段として使うことである。

## 却下した案

- 子プロセスの書き込みが親の保存より先に来ないよう、起動順序を調整する案。実装済みだったが、読んで書き戻す構造が残り、同じ形の実装が他の状態ファイルへ広がる前例になるため採らなかった。
- レジストリの更新にファイルロックを足して、読み書きを不可分にする案。`poll-pr.js` の slow 予約に同種のロックが既にあるため技術的には可能だが、そもそも子が書き戻さなくて済む設計があるのに、同期機構を増やす理由が無いため採らなかった。
- プロセスIDの記録を諦め、入れ替わったかどうかを確認しない案。確認できないまま `replaced` を返す状態は PR #472 のレビューで指摘されており、確認そのものは残す必要があるため採らなかった。
