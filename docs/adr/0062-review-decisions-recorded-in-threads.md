# レビュー指摘への決定と理由は、その指摘のレビュースレッドへの返信として残し、対応が済んだら Resolve する

## 決めたこと

工程7で人間がレビュー指摘への対応を決めたら、orchestrator がその指摘のレビュースレッドに、決定（コーダーに修正依頼／無視／保留Issueに積む）、理由、対応先を返信し、対応が済んだらスレッドを Resolve する。行に結び付けられない指摘も、ファイル単位のレビュースレッドとして投稿し、すべての指摘をスレッドにする。保留は共通の保留Issueに積む運用を変えず、保留の行と元のスレッドを相互にリンクする（#770）。

## なぜ

これまでは、トリアージの表をチャットに出すだけで、実害度と対応コストは「その場限りの提示材料。記録には残さない」と定めていた。無視と決まった指摘は何も残らず、修正依頼と保留も、どの指摘へのどの決定だったかが辿れなかった。GitHub の標準の形では、指摘ごとの決定と理由はそのスレッドへの返信として残し、Resolve で閉じる。指摘はすでにスレッドとして投稿されているため、新しい置き場所を作らずに、PR を開けば各指摘の横で決定と理由が読め、Resolve されていないスレッドがまだ対応していない指摘として見える。

## 却下した案

- 決定と理由をチャットにだけ出し、記録に残さない案（それまでの形）。GitHub への書き込みが増えず手軽に見えるが、無視した事実と理由が消え、後から辿れないため採らない。
- 指摘への決定を、PR へのコメントや Issue へのコメントにまとめて書く案。1回の投稿で済むが、指摘と決定が離れ、未対応の指摘を Resolve の状態で見分けられないため採らない。
- 保留にした指摘ごとに、スレッドから Issue を起票する案（GitHub の標準の形）。切り出しには Issue・PR・レビューの一巡のコストがかかり、保留はそのコストに見合う塊に育つまで共通の保留Issueに据え置く運用（`skills/gh-maestro-orchestrator/pending-list.md`）のため採らない。
