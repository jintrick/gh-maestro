# 一時ディレクトリの後始末は、各所の記述ではなく共有スコープの責務にする

## 決めたこと

一時ディレクトリの作成と削除を、作成と同時に所有が決まる共有スコープの責務にする。作る側が削除を書くかどうかで結果が変わる形をやめる。

作成だけを行う関数は公開しない。作成はスコープを通じてのみ行い、スコープが閉じるときに所有物をすべて回収する。後片付けに失敗した場合は握り潰さず、テスト本体の成否と区別できる形で失敗として報告する。

あわせて、この責務を迂回して `os.tmpdir()` や `mkdtemp` を直接呼ぶことを、毎回側のテストで検知する。許可する箇所はファイル単位で列挙し、件数が増えたら失敗させる（Issue #480・#481）。

## なぜ

作る側が削除を書く運用を続けた結果、消えないものが積み上がった。実測（2026-09-07）で、OSの一時領域にこのリポジトリ由来のディレクトリが 12,462件 残っていた。最古は8月30日で、最多のものは1つのテストファイルが 2,634件 を生んでいた。削除処理を一切持たないテストが10ファイルあった。

作成と削除を組にして引き受ける共有ヘルパーは存在しなかった。各テストが `withTempDir` を個別にコピーして持ち、スクリプト側は `try { unlinkSync } catch {}` を各所に並べていた。掃除する側の仕組みは存在したが、対象が狭く実際のゴミに届いていなかった。誰も見ていないため、増え続けていることに気づく機会もなかった。

これは個々の書き忘れではない。後始末を書くかどうかが呼び出し側の裁量である限り、書く人と書かない人が混ざり、混ざった状態は時間とともに悪化する。責務を1か所へ移せば、書き忘れという事象そのものが起きなくなる。

検知を併せて入れるのは、寄せるだけでは次に書かれるコードで同じことが起きるためである。移行は今あるものにしか効かない。

後片付けの失敗をテストの失敗として扱うのは、残ったものを成功扱いにすると「必ず消す」が検証できなくなるからである。

## 却下した案

- 各所に後始末の記述を足していく案。いま起きていることがその結果であり、書き忘れを防ぐ手段が「気をつける」しかないため採らなかった。
- 溜まったものを定期的に掃除するプロセスを置く案。生成元の責務の欠落を隠すだけで、掃除の対象から漏れたものは永久に残る。実際、既存の掃除する仕組みは実行時領域の空ディレクトリ 1,288件 を検知できていない。
- 掃除する側を先に直す案。同じ理由で、生成元を直すより先に安全網を広げると、責務の欠落が見えなくなる。着手順は生成元、次に実行時の場当たり削除、最後に掃除する側とした。
- 移行だけを行い、検知は入れない案。次に書かれるテストで再発するため、同じ調査をやり直すことになる。
- 溜まっている 12,462件 を先に削除する案。予防が効いたかどうかを測る基準が消えるため、削除は効果の実測後に行うことにした。
