# 管理用状態ファイルの破損は通知して止め、自動修復しない

## 決めたこと

gh-maestro の管理用状態ファイル（`workers.json`、`executions.json`、`status-pane.json` / `status-pane-recovery.json`、council の state など）が破損していた場合、削除・初期化・再構築による自動修復を実装しない。どのファイルがどう壊れているかを示して処理を止める。回復は有事に人間の指示のもとエージェントが行う。

## なぜ

破損を検知して止めるだけでは、回復手段が無いまま機能が止まる期間が生まれる。Issue #509 の時点で、`scripts/reset-session.js` は破損した status-pane レジストリを削除できず、`executions.json` には触れてもいなかった。それでも自動修復を持たせないのは、次の2つによる。

壊れ方さえ分かれば、回復はエージェントが手で行える。そのために、判定不能で停止するときは対象ファイルのパスと壊れ方の種別を示すことを Issue #509 の受け入れ条件に入れた。自動修復はこれと引き換えに破損した正本を消すため、何が起きたのかを後から調べる材料も同時に失われる。

もう一つは、起こるかどうか分からない事象に予め対処を作らないという判断である。状態ファイルの破損はまだ観測されていない。

## 却下した案

`scripts/reset-session.js` に破損レコードの削除・初期化を持たせ、回復経路を用意する案。Issue #509 の計画評価で orchestrator が提起した。fail-close を強めると `ensure-status-pane` が起動しなくなる一方、`reset-session.js` は `loadStatusPane()` が `null` を返すとブロックごとスキップするため破損レコードを削除できず、人間が手でファイルを消すまで監視ペインが出なくなるという回復経路の欠落があったためである。

採らなかったのは上記のとおり、壊れ方が分かれば人手で回復できること、および観測されていない事象に予め対処を作る必要がないことによる。
