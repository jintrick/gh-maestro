# coder が変異確認を実行する範囲を、実行する価値のあるテストに限る

## 決めたこと

coder が欠陥を実際に入れて失敗を確かめる変異確認は、追加・書き直したテストのうち、次のどちらかに当たるものに限る。

- 安全上の不変条件、または既知の不具合の再発を、単独で検出するテスト
- モック・スタブ・fixtureの作り込みや間接的な観測に依存し、対象の判定を取り除いても通るおそれをコード読解だけでは排除できないテスト

それ以外のテストでは、入れる欠陥と、その欠陥で落ちるべき理由を申告表に書けば足りる。申告表は実行した行と実行しなかった行を区別できるようにし、実行していないものを実行したように書かない。全テストを申告する決まり、Review Manager による実テストコードとの照合、変異確認の有無で commit・push・merge を止めない決まりは docs/adr/0051-test-quality-by-declaration-and-verification.md のまま維持する。0051 のうち変わるのは、変異確認の対象を「新規・書き直しのテストすべて」とした部分だけである。

## なぜ

人間が Issue #756 で、coder が自分の書いたテストを1件ごとに壊して再実行する作業が、トークン使用量と作業時間に見合うかを問うた。この作業は件数に比例して増える。単純で、読めば検出対象が分かるテストにも同じ実行コストを払っている。確認は自分が書いたテストを自分で入れた欠陥で試すもので独立性が弱く、その後に Review Manager が実テストコードと申告を突き合わせる。実行が効くのは、読解だけでは欠陥検出能力を判断しにくいテストである。

## 却下した案

- **全テストへの実行義務を維持する**: 0051 の決定そのもの。質の低いテストが入る経路を塞げるが、コストが件数に比例し、読解で足りるテストにも払う。人間が負担に見合わないと判断した。
- **実際のトークン使用量・作業時間を測ってから範囲を決める**: 人間が「測るのはやめろ」と明示して却下した。
- **実行を、受け入れ条件に直結するテストだけに限る**: 0051 が却下した案。受け入れ条件との結び付きは、読解で検出能力を判断できるかと対応しない。このため採らず、テストの性質（単独で守る不変条件・回帰か、間接検証か）で線を引いた。
