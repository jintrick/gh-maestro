# spawn-worker のセッションガードはセキュリティ境界ではない

## 決めたこと

`scripts/spawn-worker.js` のセッションIDガードは、スキルをロードしていないセッションに `/gh-maestro` の実行を促すためのものであり、ローカルシェルからの意図的な迂回を防ぐ認可境界ではない（Issue #444・PR #445）。

`SESSION_ID` は workspace 配下の平文ファイルに置かれ、`scripts/get-context.js` を実行すれば任意のシェルから取得できる。これは既知の上で許容する。

## なぜ

防ぎたい事故は1つだけである。スキルをロードし忘れたセッションがワーカーを起こし、報告を受け取る監視が張られないまま工程が進むこと。Issue #423 で実際に起きた。

ガードが相手にするのは AI エージェントであり、拒否されればエラーメッセージの指示に従う。したがって「`/gh-maestro` を実行してください」と伝えるだけで目的を果たす。

ファイルを正本とする限り、同じマシンのどのシェルからも値は読める。この穴を塞ぐには、外部シェルが再現できない実行コンテキストへ結び付けるしかないが、その手段はいずれも別の代償を伴う。事故の防止という目的に対して、代償が釣り合わない。

この判断を記録するのは、迂回可能であることが自動レビューで繰り返し BLOCKER として指摘されるためである。PR #445 でも指摘された。経緯が残っていないと、そのたびに脅威モデルの議論をやり直すことになる。

## 却下した案

**Claude Code の環境変数（`CLAUDE_CODE_SESSION_ID`）に結び付ける。** 外部シェルからは再現できないため穴は塞がる。orchestrator の Claude Code 依存を増やさない方針により却下した。gh-maestro は複数のエージェントCLIを扱う基盤であり、orchestrator の実行経路を特定CLIの内部仕様に結び付けない。

**親プロセスを辿ってセッションを特定する。** 実測したところ `findSessionRootPid()` は `maxDepth = 5` で打ち切るため、Claude Code のプロセスではなくその親のシェルを返した。端末のシェルはセッションより長生きするため、同じ端末で開いたスキル未ロードのセッションを通してしまう。`scripts/shared/ensure-worker-supervisor.js` に、子プロセスへセッション解決を委ねて誤判定した同種の実障害の記録がある。方式として成立しないため却下した。
