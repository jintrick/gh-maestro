# 質問はターンの終了として扱い、停止をワーカー自身の終了で成立させる

## 決めたこと

ワーカーが orchestrator へ質問を投げる行為を、「実行の完了」ではなく「入力を要求してそのターンを終える」という中間終端として扱う。ワーカーは質問を公開したらそのターンを終了し、回答は既存の再開（resume）配送でのみ受け取る。停止はワーカー自身がターンを終えることで成立させ、送信スクリプトにも監視プロセスにも停止責務を負わせない（Issue #440）。

## なぜ

質問を投げたワーカーが止まらないという不具合の原因は、送信経路ではなく、質問後のワーカー状態が定義されていなかったことにある。監視プロセスは生存中のワーカーへ入力を注入せずメッセージを保留に回すため、プロセスを生かしたまま待つ実装は、回答が原理的に届かない。実際に Issue #438 で、質問を投稿したワーカーが回答を得ないまま調査を続け、計画まで投稿した。

質問を中間終端として定義すると、報告して停止し再開されるという既存パターンをそのまま流用でき、待機ループを新設せずに済む。同時に、質問を最終報告と取り違えて実行を完了扱いにすることも、回答待ちのワーカーを居座りと誤認することも防げる。

## 却下した案

- 送信スクリプトに質問モードを設け、投稿後に呼び出し元のワーカーを停止させる案。子プロセスが親のエージェントプロセスの寿命を制御することになり、投稿は成功したが停止に失敗したという部分成功を生むため採らなかった。同じ入口の中で回答を待たせる案も、ワーカーを作業中のまま残して再開配送の前提を崩すため採らなかった。
- 監視プロセスが質問を識別してワーカーを停止させる案。停止までに作業が進む競合窓が消えず、監視機構が業務プロトコルの正しさを担うことになるため採らなかった。監視の役割はプロトコル違反の検出と可視化に留める。
- ワーカー手順に「質問したら終了する」と書くだけで、契約上は区別しない案。質問と最終報告を機械的に見分けられず、違反しても居座りとしてしか見えないため、これ単独では採らなかった。
