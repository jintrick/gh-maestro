# エージェント定義の引数は、受け継ぎの段ごとに保持して、用途ごとに組み立てる

## 決めたこと

エージェント定義が `extends` で基底を受け継ぐとき、設定の解決（resolve-config.js）は、基底と派生の引数を1本に混ぜて由来を捨てず、受け継ぎの段ごとの定義を保持する。普段用と計画用の引数は、段ごとに上から順に足し合わせて作る。計画用は、その段に `planExtraArgs` があればそれを、無ければその段の `extraArgs` を使う。不正な値の検査・警告・フォールバックは設定の解決の中だけで行い、起動・再開の側（agent-launch.js）は、解決済みの引数から用途に合うものを選ぶだけにする。既存の読み手が使う平坦な `extraArgs` は、普段用の解決済みの引数として今と同じ中身で残す。config.json の書き方は変えない（Issue #725、architect の設計コメント https://github.com/jintrick/gh-maestro/issues/725#issuecomment-6572610522 ）。

## なぜ

受け継ぎの時点で引数を1本に混ぜると、後から「どれが基底の必須の引数で、どれが定義自身が足した引数か」を区別できない。#725 で計画用モデルに差し替えようとしたとき、混ぜたリストを置き換えたため、基底から受け継いだ非対話の指定・権限の指定・タイムアウトまで消えた。人間はこれを「ちょっと拡張しようとするとボロが出る作り」と判断し、根本からの見直しを求めた。段ごとに保持しておけば、用途が増えても、受け継ぎが何段になっても、同じ仕組みで組み立てられる。

## 却下した案

- 基底の定義の必須の引数を `baseArgs` などの別の欄に分け、`extraArgs` と `planExtraArgs` を定義自身の上乗せ専用にする案。2段の受け継ぎなら明快だが、3段以上で途中の段が足した引数が再び混ざる。基底の定義の書き方と検査、既存のテストの書き換えも要る。
- 各段で、親の解決済みの引数に定義自身の引数を連結し、`planExtraArgs` の欄そのものを完成した配列に書き換える案。senior-coder の改訂計画の方式で、変更は小さい。しかし元の設定の値と解決後の値が同じ名前の欄で衝突し、不正な値の検査をどこで行うかが曖昧になる。
