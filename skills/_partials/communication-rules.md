## 通信ルール

作業の結果・質問・相談・報告は、必ず次のコマンドをツール呼び出しとして実行して伝える（送信元・宛先・Issueは環境から自動確定される）：

```sh
node "{{SCRIPTS_PATH}}/msg-send.js" --body-file <本文ファイルのパス>
```

本文をファイルに保存して渡す方法がシェル非依存の推奨例です。標準入力を使う場合は、使用中のシェルに合わせて次の例を使ってください。

PowerShell:

```powershell
@'
<内容>
'@ | node "{{SCRIPTS_PATH}}/msg-send.js" --stdin
```

Bash:

```bash
node "{{SCRIPTS_PATH}}/msg-send.js" --stdin <<'EOF'
<内容>
EOF
```

`<内容>`は本題のみを書く。前置き・相槌・言い換え予告（「〜について、わかりやすくお伝えしますね」等）は書かない。読み手はorchestrator（同水準の別インスタンス）であり、平易な説明への配慮は不要かつ雑音（トークン浪費・可読性低下・余分なスクロール）でしかない。

**NG例:** 「ご提示いただいた文章を、専門知識がなくても一発でイメージできるように噛み砕いてお伝えしますね！」で書き始めてから本題に入る。
**OK例:** 前置きなしで本題（報告テンプレートの先頭行）から書き始める。

本文は必ず`--stdin`（上記）または`--body-file <path>`で渡す。位置引数で渡すと`msg-send.js`がエラーで拒否する（短い本文でも例外はない——過去にバッククォート/`$`入りの報告が「短いから大丈夫」という判断で位置引数のまま送られ、bashに解釈されて黙って壊れ、GitHubへの二重投稿事故になった）。

**Bashでヒアドキュメントを使う場合は、終端記号を必ずクォート付き（`<<'EOF'`）にすること。** クォート無しの`<<EOF`は`msg-send.js`側では検出できず、本文中のバッククォート・ドル記号がヒアドキュメント内でも展開されてしまい同じ事故が再現する。着手報告（「〜します」等）は送らない。指示を処理したら結果を返信する（ackは不要）。

すべての作業を終えたら、最終出力には `DONE` の1語だけを書く。

## 常駐プロセスに関する制約

本番ワークスペースで稼働している常駐プロセス（`worker-supervisor` 等）を、検証等の目的で強制置き換え（`--force`）してはならない（常駐プロセスは gh-maestro が動くための土台であり、ワーカーの作業対象ではないため。置き換えると全ワーカーへの指示配送が停止するなどシステム全体が停止する）。常駐プロセスの動作確認や内部検証を行う場合は、必ず自分専用の一時ワークスペースを作成して行うこと。
