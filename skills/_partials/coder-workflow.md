## ゴール

PRを作成した時点で実装作業は完了する。CI監視はorchestratorの責務であり、コーダーは行わない。実装完了後の報告は不要（orchestratorがPRを自律検出する）。

## 手順

{{RULES_CHECK_STEP}}
1. `node "{{SCRIPTS_PATH}}/msg-read.js" --issue-context --issue $ISSUE --workspace $WORKSPACE` で宛先フィルタ済みのIssueタイトル・本文・コメント一覧を読み、Issueの要件を把握する
2. **作業前に質問事項がある場合は通信ルールのコマンドでorchestratorに質問し、返答を待ってから作業を進める**
   実装中に追加の判断が必要になった場合も、通信ルールの既存コマンド `node "{{SCRIPTS_PATH}}/msg-send.js" --body-file <質問本文ファイルのパス>` で質問を投稿する。質問の投稿が成功したら、そのターンで追加の調査・実装・計画・完了報告を続けず、ワーカー自身の手順を終了する。回答は次の resume で受け取る。
   理由と経緯: `docs/adr/0027-question-is-turn-end-not-completion.md`
3. **計画フェーズ（実装着手前に必須）**:
   - `$WORKTREE` 上で実装計画に必要な調査（対象ファイル・変更方針・作業分割・検証条件）を行う
   - 実装計画を `$WORKSPACE/.gh-maestro/plans/<issue>.md` にMarkdownファイルとして作成する（worktree は後で削除されるため、計画はworktree の外の per-workspace 領域に残す）
   - 計画には、受け入れ条件ごとに「テストが検出すべき欠陥」を1行で書く欄を設ける。欠陥を検出するテストが描けない受け入れ条件は、その旨を書く
   - 理由と経緯: `docs/adr/0051-test-quality-by-declaration-and-verification.md`
   - `publish-plan.js` で計画をIssueのpin済みコメントとして投稿し、そのURLからコメントIDを取る：
     ```sh
     PLAN_URL=$(node "{{SCRIPTS_PATH}}/publish-plan.js" --issue $ISSUE --body-file <計画ファイル> --workspace $WORKSPACE)
     PLAN_COMMENT_ID=${PLAN_URL##*#issuecomment-}
     case "$PLAN_COMMENT_ID" in ''|*[!0-9]*) echo "計画コメントURLからIDを取得できません: $PLAN_URL" >&2; exit 1;; esac
     ```
     スクリプトが自動的に新規投稿（初回）か既存pinコメントの更新（差し戻し後）かを判定するため、コーダー側で分岐する必要はない
   - pin 済みコメントのURLだけを書いた本文ファイルを作り、`msg-send.js --plan-comment-id <ID>` で報告する。**本文はURLだけとし、計画の要約・概要・要点を含めない。** `msg-poll.js` はcarrier報告を報告済みとして認識したうえで `PLAN_REPORTED` を1回出し、`NEW_MESSAGE` は重ねて出さない。計画コメント自体はhookが読む通知IDであり、stage-5の手順書はorchestratorの文脈だけに届く。
     ```sh
     printf '%s\n' "$PLAN_URL" | node "{{SCRIPTS_PATH}}/write-draft.js" /tmp/plan-url-<N>.md --stdin
     node "{{SCRIPTS_PATH}}/msg-send.js" --plan-comment-id "$PLAN_COMMENT_ID" --body-file /tmp/plan-url-<N>.md
     ```
     この報告を送った時点で1アクション完了とみなし、**そのまま終了してよい**（承認または差し戻しが届いた時点でorchestratorから再開される）
   - **承認の指示を受け取ったら**、以下の手順4に進む
   - **差し戻し（修正依頼）の指示を受け取ったら**、計画を修正し、再度 `publish-plan.js` で同じpin済みコメントを更新し、再度報告して待機する
4. `$WORKTREE` 上で実装を完了させる（作業は必ず `$WORKTREE` 内で行う）
5. **新規追加・修正したファイルに対応するテストケースを作成し、宣言された毎回側のランナーを全件実行する**
   - テストを追加・変更する前に、`$WORKTREE` の `.claude/rules/test-quality-criteria.md` を `Read` ツールで読む（`paths` による自動読み込みには頼らない）。そのうえで、テストは基準の4条件（検証目的・期待値の独立性・欠陥検出能力・追加価値）を満たすものだけを書く
   - 追加・書き直したテスト1件ごとに、後で申告表（HEAD付きのPRコメント）へ次の4項目を表で書けるよう、作業中に控えておく: ①テスト（ファイル:行・名前）、②何が壊れたら失敗するか、③期待値の出所（仕様・要件・既知の正解・外部契約のどれか）、④入れた欠陥と結果（または実施しない理由）
   - 新規・書き直したテストすべてについて、そのテストの「何が壊れたら失敗するか」（②）に書いた欠陥を実際に入れて失敗することを確かめる（変異確認）。確かめられない場合は、実施しない理由を④に書く。結果の記録は、確かめた事実（入れた変更・失敗したテスト名）に限り、結果の数値を手で作らない
   - 削除・統合したテストがあれば、表とは別に「削除・統合したテスト」の欄を設け、統合先が何を検出するかを書く
   - 理由と経緯: `docs/adr/0051-test-quality-by-declaration-and-verification.md`
   - テスト結果の申告は、test runner が生成した機械可読な成果物からのみ行われる。fail/pass の数値を手で数えたり、申告用に入力したりしてはならない。成果物が生成されない環境では申告は `unknown` になるが、それを手入力で補ってはならない。文書だけの変更を除き、成果物が無い状態で `push-and-declare.js` を実行してはならない
   - コーダーの完了条件は「全件を実行し、結果が残ること」であり、「全件が pass すること」ではない。赤い結果でも次の push・PR・申告へ進む
   - **失敗側・拒否側の経路を必ずテストする。** 検証・ガード・エラー分岐を追加したなら、「正しく通ること」だけでなく「**正しく拒否されること**」を検証するテストを書く。ロックが取れないとき、ファイルが読めないとき、外部コマンドが失敗したとき、必須の引数が無いとき——それぞれで処理が期待どおり中断し、危険な操作が実行されないことを固定する
   - 成功側だけを検証したテストは、フェイルクローズが実際に閉じることを保証しない。「テストは緑だが、守るべき性質は守られていない」状態を作る
   - **検証したい判定そのものをモックで飛ばさない。** 判定の結果（`running: false` 等）を fixture へ注入して期待値にすると、判定ロジックが丸ごと壊れてもテストは緑になる。差し替えてよいのは判定の入力（実在しないPIDを置く等）であり、判定そのものではない
   - 自分の変更に起因しない既存テストの失敗は修正しようとしてはならない。そのまま実行結果として残し、申告して、修正するかどうかは orchestrator と人間に委ねる
   - テスト層が分かれているプロジェクトでは、`node "{{SCRIPTS_PATH}}/run-tests.js" --workspace $WORKSPACE --list` を実行し、出力された宣言済み層の `name` と `scope`（`full` / `partial`）を確認して、プロジェクトの規約に従って実行する。実行コマンドと変更ファイルの対応は `run-tests.js` に委ね、設定ファイルを直接読んではならない。重要度、壊れやすさ、担当者の判断で範囲を変えてはならない
      - 反復中は宣言された毎回側の層だけを実行する
      - `slow` 層はコーダーの宣言対象ではない。`run-tests.js slow` は主体認可を持ち、PR検出後の `poll-pr.js` から渡された実行主体だけを受け付ける。コーダーは slow を直接実行せず、`poll-pr.js` がPRの対象HEADごとに一度だけ起動した結果と層別成果物を待つ
     - 変更したファイルに対応する分離側テストが宣言されていれば、その層を対応するテストファイルへ絞って実行する
     - 対応するテストが無い変更、または分離側が宣言されていない場合は、宣言された毎回側の層を実行する。層名・コマンド・対応規則を推測してはならない
   - テスト層が分かれていないプロジェクトでは、宣言された唯一の層を全件実行する
   - **テストを層へ振り分ける単位はテスト関数である。テストファイルではない。** 1つのファイルに両方の性質のテストが同居していたら、ファイルごと移さずに分割する。遅い関数が1つあるという理由で、同じファイルの速い関数を毎回側から外してはならない
   - 分離側へ置くのは、次のいずれかを含むテスト関数だけとする
     - 起動に時間がかかるもの（実プロセスの起動、実git操作、実シェルの起動）
     - 実際に時間を待つもの（スリープ、タイムアウト待ち）
   - モックへの差し替えで済んでいるものは分離側の対象ではない。呼び出しの形が似ていても、実際に外部を起動していなければ毎回側に置く
   - 重要度・壊れやすさ・保証価値を振り分けの理由にしてはならない。上の2つに当たるかどうかだけで決める
   - 新しいテストを書くときも同じ基準で置き場所を決める。既存ファイルにあるからという理由で追随させない
   - slowテストは、テスト関数1件を単独で実行して20秒以内に完了させる。超える場合は待ち時間・ポーリング間隔・タイムアウト値の注入などで短縮し、短縮できなければ廃止して、必要なときだけ行う実機確認手順を残す。commit・push・mergeを機械的に止める検査にはしない
   - 実行は宣言されたランナー経由で行い、成果物に残った終了コード・実行範囲・件数・lint/型チェック記録を `push-and-declare.js` に引き渡す。毎回側の実行では lint を同じ成果物へ記録し、scope=full では package.json に `typecheck` スクリプトがあれば `npm run typecheck` を実行する。未定義・成功・失敗・起動不能を区別して記録する。lint と型チェックの結果はテストの失敗や終了コードへ変換せず、申告コメント、`TEST_STATUS` 通知、`query-test-status.js` 照会へ伝える。必須のlintまたは型チェック記録が欠落・古い・破損している場合は申告を完了させず、`run-tests.js` の再実行を促す。結果の数値を手入力してはならない
     - 実行入口は `node "{{SCRIPTS_PATH}}/run-tests.js" --workspace $WORKSPACE <一覧で確認した層名>` とし、分離側の変更対応を使うときは `--changed` と変更ファイルの相対パスを渡す
6. **初回実装完了時・レビュー指摘対応の修正push時に、ステージング・コミット・push・PR取得/作成・テスト結果申告を一つの操作にまとめた `push-and-declare.js` を実行する**:
   申告表は、PR の差分全体（基底ブランチ `$BASE_BRANCH` から HEAD まで）に含まれるテストについての表で、**push のたびに必ず** `--declaration-file` で出す。判定はしない（テストに触れない push でも出す）。
   - PR の差分にテストの変更（追加・書き直し・削除・統合のいずれか）が無い回は、表の代わりに「テストの変更なし」とだけ書く。
   - PR の差分にテストの変更がある回は、テストごとの表を書く（下の列の規則に従う）。
   - 表は前回の表（`$WORKSPACE/.gh-maestro/pr-declaration-$ISSUE.md`）を基に、今回の push で変わったテストを反映して全体を書き直す。テストに触れない push では内容を変えずに出し直す。
   - ファイルは heredoc（`cat >`）で直接作る（`write-draft.js` は `/tmp` 配下しか書けない）。
   ```sh
   DECL_FILE="$WORKSPACE/.gh-maestro/pr-declaration-$ISSUE.md"
   cat > "$DECL_FILE" <<'EOF'
   <手順5で控えた申告表。テストの変更が無い回は「テストの変更なし」の一文>
   EOF
   ```
   ```sh
   node "{{SCRIPTS_PATH}}/push-and-declare.js" --issue $ISSUE --workspace $WORKSPACE --declaration-file "$DECL_FILE"
   ```
   - 申告表は `push-and-declare.js` が、対象コミット（HEAD）の SHA を持つ PR コメントとして投稿する（同じHEADのコメントがあれば更新する）。PR 本文には触れない。既存PRは push の前に投稿する。新規PRは下書きで作られ、申告表の投稿が済んでから公開される（公開されるまで Review Manager は始まらない）。レビューは自分がレビューする HEAD に一致する申告表だけを使い、無ければそのことを事実として扱う。
   - 申告表は、新規・書き直したテスト1件につき1行で、列は「テスト（ファイル:行・名前）」「何が壊れたら失敗するか」「期待値の出所」「入れた欠陥と結果（または実施しない理由）」。その下に「削除・統合したテスト」の欄を置く。
   - 削除・統合したテストは、「削除・統合したテスト」の欄に、削除したテスト名と統合先が何を検出するかを、差分全体の分について書く。
   - この一連の操作は「終状態への収束」として定義されており、同じコマンドの再実行だけで回復する（コミットすべき変更が無い場合は空コミットを作らず、その段をスキップする）
   - コミットメッセージは `impl(issue-<N>): <Issueタイトル>` に固定される（モデル推論を挟まない）
   - PRは get-or-create（既存PRがあれば使用、無ければ作成）。初回か修正かを自分で判定する必要はない
   - 理由と経緯: `docs/adr/0051-test-quality-by-declaration-and-verification.md`
   - 申告は直前のテスト runner が生成した成果物から fail/pass、実行範囲、lint/型チェック記録を読み取る（テストが赤でも終了コードは0）。宣言された毎回側の成果物またはlint/型チェック記録が欠落・古い・破損・対象外の場合、`push-and-declare.js` は push 後に非ゼロ終了する。文書だけの変更はテスト結果を要求せず、従来どおり進む。lintの指摘と型チェックの失敗・起動不能・未定義は停止条件にせず、数値を手入力して補ってはならない。申告後の両状態は同じ `TEST_STATUS` / `query-test-status.js` 経路で確認する
   - **素の `git commit` / `git push` / `gh pr create` を直接実行しない**（このスクリプトが一括で行う。個別実行すると申告を省く経路が生まれ、orchestratorがSTALE/NONE申告の検知で待たされる）

## 失敗時

```sh
node "{{SCRIPTS_PATH}}/msg-send.js" --stdin <<'EOF'
実装に失敗しました。
EOF
```

## 制約

- `main` への直接pushは禁止
- `$WORKTREE` ルートで `npm install` / `npm ci` は実行しない。ルートで npm install を実行するとワークスペース共有の `node_modules` を破壊する
- 実装で新しいサブパッケージ（例: `gui/`）を追加した場合、そのディレクトリ内での `npm install` は許可する（`cd gui && npm install`）

- 実機での確認（対話型セッションでの動作確認、常駐プロセスの起動・停止を伴う確認など）でも、本物のワークスペースの状態ファイル（`workers.json` 等）・本物の Issue / PR、およびユーザー領域（`~/.claude/`、`~/.gh-maestro/`）を書き換えない。一時的なワークスペースと隔離した対象で行う。隔離できない確認が必要な場合は、実施せずにその事実を報告し、orchestrator の判断を仰ぐ
