## 手順

1. 対象プロジェクトのテスト実行方法を調べる。`package.json` の scripts、テストランナーの設定、テストの配置、既存のテスト用CLIを確認し、通常のテストと実プロセスを起動するテストや実時間を待つテストを区別できる材料を集める。コマンドが実際に動くかの検証は、層の宣言を作る作業とは分けて扱う。

2. テストを**テスト関数単位**で毎回実行する層と分離する層へ分類する。分離するのは、実プロセスの起動・実git操作・実シェルの起動など起動に時間がかかる関数、またはスリープ・タイムアウト待ちなど実際に時間を待つ関数だけとする。モックだけで外部起動を置き換えている関数は毎回側に置く。1つのファイルに両方の関数がある場合は、関数を削除・統合・改名せず、必要な範囲でファイルを分割する。

   重いテスト用のディレクトリは、対象プロジェクトに既存の `slow`、`integration`、`e2e` などの規約があればそれを使う。規約が無ければ、対象プロジェクトのテストルートを基準にした名前（例: `<test-root>/slow`）を提案し、プロジェクト固有の設定として決める。特定プロジェクトのディレクトリ名を他プロジェクトの標準として仮定してはならない。

   重いテストが1つも無い場合は層を分けず、毎回実行する単一の層だけを宣言する。重要度、壊れやすさ、保証価値を分類理由にしてはならない。

3. 分類案と `config.json` の設定案を人間へ提示する。毎回側・分離側の層名、各層の実行コマンド、対象テストファイル、変更ファイルとテストの対応規則、重いテストを置くディレクトリ、ファイル分割・移動の一覧を含める。この段階では、テストファイルの移動・分割、`config.json` の作成・変更、その他対象プロジェクトのファイル変更を一切行わない。人間の承認を得るまで待つ。

4. 承認を得たら、分離対象のテスト関数を専用ディレクトリへ移す。毎回側と分離側の関数が同じファイルに混在している場合は、まず両方の関数を失わないようにファイルを分割し、その後に重い関数だけを移す。テスト関数を削除・統合・改名せず、移動と分割だけを行う。移動前後でテスト関数の総数が減っていないことを確認する。

5. 対象プロジェクトの `.gh-maestro/config.json` に `test.layers` を書く。毎回側と分離側の両方（分離対象が無い場合は単一層）の `scope`、argv配列の `command`、既定の対象ファイル、必要な `fileArgs`、表示用コマンド、変更ファイルから対象テストを選ぶ `mapping` を宣言する。パスはworkspaceからの相対パスにし、シェル文字列ではなくargv配列を使う。分離側の `scope` は `partial`、全件を実行する毎回側の `scope` は `full` とする。実在しない層を将来のために追加してはならない。

6. 宣言した毎回側と分離側の両方を、共有ランナー経由で実行する。各層で実行範囲と結果を確認し、宣言と実際の配置が一致していることを確認する。実行結果を人間へ報告する。結果が失敗した場合は、失敗した層・実行範囲・原因を報告し、テスト関数の削除や層の水増しで隠してはならない。

   ```sh
   node "{{SCRIPTS_PATH}}/run-tests.js" --workspace $WORKSPACE <declared-layer>
   ```

7. 設定とテスト配置の承認済み変更、両層の実行結果を人間へ報告してから、`/gh-maestro` の起動手順へ戻る。`TEST_LAYERS_STATUS=declared` を確認したうえで、`gh-maestro-orchestrator` スキルを読み、orchestratorとして動作を開始する。
