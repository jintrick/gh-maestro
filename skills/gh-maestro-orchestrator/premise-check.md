# 前提を疑う問い（参照専用）

orchestrator は、今ある仕組みの形を前提に問題を直そうとしがちである。標準の形や既存のライブラリに戻せば問題そのものが消える場合でも、それを確かめずに自前の実装を重ねてしまう。この文書は、工程1と工程5で使う共通の定義、それぞれの場面と問いを定める。手順は `stage-1-requirements.md` と `stage-5-plan-review.md` にある。

## 共通の定義

### 疑う対象の仕組み

自前で作る、維持する、または変更する仕組みのうち、状態の同期、再試行、待ち行列、キャッシュなど汎用的なものと、汎用性を問わずセキュリティに関わるものを対象にする。各工程で疑いを向ける場面は、それぞれの節に定める。

### explorer への依頼の共通原則

依頼には達成したいことと、確認してほしい事実を書く。候補の設計や選んだライブラリ、「Xで足りるか」という問いを調査の枠にしない。人間や前のワーカーが挙げた案は、標準の形を調べる対象の1つとして渡す。

工程1では、課題を症状や現在の仕組みではなく達成したいことに言い換え、今の形・標準の形・両者の差を尋ねる。工程5では、計画が手を入れる箇所に残る自前の仕組みを列挙し、それぞれを置き換えうる標準の手段を事実と出典付きで調べる。工程ごとの依頼内容は各節に従う。

### Issueコメントとチャットの書式

Issueコメントは冒頭に結論を置き、問いごとに見出しを分け、標準の形など外部の事実には出典リンクを付ける。工程ごとの結論と見出しは各節の書式に従う。チャットには結論とコメントURLを示す。手順上、人間に問わないときの事後報告は、参照する工程の指示どおり1行にする。

## 工程1: 要件確定

### 疑いを向ける場面

次のどれかに当たるとき、4段の問いに答える。

- 汎用的な仕組み（状態の同期、再試行、待ち行列、キャッシュなど）を自前で作る、または持ち続けている。
- 同じ領域で手直しが続いている（`stage-1-requirements.md` の1-[2/5]で見つける）。
- セキュリティに関わる仕組みに触れる（上の兆候が無くても常に当たる）。

想定外の動作（バグ）は、単発であれば当たらない。作った意図とのずれを直すだけで、形を問うものではないからである。ただし、同じ領域でバグの修正が続いているなら、2つ目の場面に当たる。

当たらないと判定したときも、その根拠を人間に発言する。黙って省かない。

### 4段の問い

解決策を考える前に、次の4段に順に答える。各段は「問題なし」「該当なし」の一言で済ませず、中身を書く。

1. **今の形**: 問題が起きている仕組みは、いまどういう形か。
2. **標準の形**: 同じ課題に対する世の中の標準の形は何か。出典を付ける。
3. **標準に戻した場合**: 問題は消えるか。何が残るか。
4. **要求の成否**: Issueの要求はそのまま成り立つか。成り立たないなら、どう変えるか。

1段目と2段目は、explorer の調査（`stage-1-requirements.md` の1-[3/5]）から書く。3段目と4段目は、orchestrator が1・2段目から判断して書く。調査しなかった段は、分かる範囲だけを書き、細部を作らない。

4段目で要求が成り立たないときは、作業を進めず、人間にIssueの見直しを諮る。書き直すか、閉じるか、そのまま続けるかは人間が決める。

### explorer への依頼

依頼は次の形で書く。

- **課題**: 症状でも今の仕組みでもなく、達成したいこととして言い換えて書く。例:「保存中に操作が効かない」（症状）や「保存の直列化」（今の仕組み）ではなく、「フォームの編集をすぐ画面に反映し、裏で自動保存する」。
- **問うこと**: 今の形（今の実装、まだ無ければ予定している実装）、標準の形（外部の事実と出典）、両者の差、の3つ。
- **書かないもの**: 候補の設計、選んだライブラリ、「Xで足りるか」という形の問い。人間や前のワーカーが挙げた案は、標準の形の調査対象の1つとして渡すだけで、問いの枠にしない。

### 答えを書くIssueコメントの書式

```md
## 前提の確認（4段の問い）

> **結論: 要求はそのまま成り立つ ／ 要求を見直すべき**
> （1〜3から言えることを1〜2文で）

### 1. 今の形
根拠: explorer 調査 ／ 調査なし

**要点を1文で。**
- 根拠となる事実

### 2. 標準の形
根拠: explorer 調査 ／ 調査なし

**要点を1文で。**
- 定番の作り・ライブラリ・既定（出典のリンク）

### 3. 標準に戻した場合
**消える問題と残る問題を1文で。**
- 消えるもの
- 残るもの

### 4. 要求の成否
**成り立つ ／ 成り立たない。**
- 成り立たないなら、要求をどう変えるべきか
```

チャットには、冒頭の結論の1〜2文とコメントのURLだけを示す。

## 工程5: 計画評価

### 問いを向ける対象と4つの問い

対象は課題ではなく、計画が実現手段として作るものと、計画が手を入れる箇所に残る仕組みである。第1問に仕組みが1つ以上挙がった場合に、残る3問にも答える。標準ライブラリの使い方が正しいかどうかは、コードを見るレビューの役割とし、工程5では問わない。

1. **自前の仕組み**: 計画が自前で作る、または計画が手を入れる箇所に残る仕組みのうち、汎用的なもの（状態の同期、再試行、待ち行列、キャッシュなど）と、汎用的かどうかを問わないセキュリティに関わるものは何か。
2. **代わりになる標準の手段**: それぞれについて、プロジェクトが既に使っているライブラリやフレームワークの機能、または定番のライブラリで代わりになるものはあるか。出典を付ける。工程1の「前提の確認」コメントがあれば、そこで合意した標準の形に含まれるかも示す。
3. **土台への乗り方**: 計画は標準の形を土台として使っているか。一部だけを部品として使い、残りを自前で並べていないか。
4. **結論**: 理由とともに、次のいずれかを選ぶ。
   - 計画のまま進めてよい。
   - 計画を差し戻し、自前の部分を標準の手段に置き換える。
   - Issueの要件そのものが標準の形とぶつかるため、人間にIssueの見直しを諮る。

### explorer への依頼

5-[1/3] の既存パターン照合と同じ依頼に、次を含める。新たな許可は求めない。

- 計画本文から、計画が新たに作る仕組みを拾って渡し、計画が手を入れる箇所に残る自前の仕組みを事実として列挙させる。
- 列挙した仕組みすべてについて、既存の依存が持つ機能、代わりになる定番のライブラリ、各候補の根拠となる出典を調べさせる。
- 既存パターンや共用部品の呼び出し元を調べる場合も、計画との重複・前提の差を事実として報告させる。
- 修正版計画では前回から変わった部分だけを調べ、変更された仕組みについて答え直させる。

依頼は、計画の手段を問いの枠にせず、仕組みの列挙と標準の手段に関する事実・出典を求める。第1問に該当する仕組みが無ければ、工程5の問いへの回答コメントは投稿しない。

### 答えを書くIssueコメント

該当する仕組みがある場合、承認または差し戻しの指示より前に `comment-issue.js` でIssueへ投稿する。結論を冒頭に置き、4問ごとに見出しを分け、標準の手段など外部の事実には出典リンクを付ける。結論には工程5の4つ目の選択肢とその理由を書く。

人間に問わない場合の事後報告は、結論とコメントURLを1行で示す。仕組みが無く対象外の場合は、コメントを投稿せず、対象外の根拠だけを1行で示す。どちらも `SKILL.md`「通知と応答」に従い、末尾を「—」にする。
