# 工程 5. 計画評価【必須】

このファイルは、同じIssueを担当するorchestratorが工程5で実行する手順の正本である。工程番号・必須／任意・入口／待機／遷移を確認して進める。人間への発言と工程横断の不変条件はSKILL.mdに従う。

<!-- gh-maestro-structure: middle-items=3 -->

入口: PLAN_REPORTED:<issue>:<planCommentId>を受けたとき。待つもの: 評価に必要な報告。人間の判断を要する論点が残る場合と、architect の計画レビューを問う場合は人間の回答。次: 承認または差し戻しで工程6、更新計画の報告後は工程5を再実行。

計画の承認は orchestrator が持つ。orchestrator が承認推奨と評価した計画は、初回か修正版かを問わず、人間に提示も質問もせず実装を開始する。人間に問うのは、範囲など人間の判断を要する論点が残っているとき、Issueの見直しを要するとき、architect の計画レビューを依頼するか決めるときだけである。人間に問わない決定後の1行報告は、承認や質問ではなく工程の事後報告として行う。

中項目の番号は、人間に名乗る場面に振る。5-[1/3]はorchestratorの内部作業であり、問いや工程番号を人間に示さない。人間に声をかけるのは、5-[2/3]でarchitectへの依頼を問うときと、5-[3/3]で人間の判断を要する論点を問うときである。

#### 5-[1/3] 計画の評価【必須】

次を上から順に行う。

- **計画の取得**: 計画URL報告が `msg-poll.js` で分類された `PLAN_REPORTED` を受け取ったら、Issue番号を指定して計画本文を取得する:

   ```sh
   node "{{SCRIPTS_PATH}}/msg-read.js" --plan --issue $ISSUE --workspace $WORKSPACE
   ```

- **orchestrator自身による一次評価**: 計画本文をIssue本文の要件定義と照合し、以下を確認する：
   - 要件定義の全項目が計画でカバーされているか
   - 変更方針・作業分割が要件に対して妥当か
   - 受け入れ条件を満たせそうか
   - 受け入れ条件ごとの「テストが検出すべき欠陥」の欄が計画にあるか。欄が無い場合、または受け入れ条件と対応していない場合は、見落としとして扱う
   - 明らかな見落としやリスクがないか

   **見落としが無ければ「無い」と判定して終える。** 評価した形を整えるために懸念を作らない。実質のない懸念は差し戻しや人間への問いを生み、判断の材料ではなく雑音を増やす。

- **既存パターンの照合と工程5の問い**: 計画に含まれる具体的な実装要素（新設する処理・追加するモジュール・採用するアルゴリズム等）について、`gh-maestro-explorer` に類似の既存実装・共有ヘルパーの有無を調査させる。特定の1ファイルを「参考実装」として示させず、共有ヘルパーの有無を確認させる。

   同じexplorer依頼に、`{{SHARED_SKILLS_PATH}}/gh-maestro-orchestrator/premise-check.md`（共通の定義）と `{{SHARED_SKILLS_PATH}}/gh-maestro-orchestrator/premise-check-stage-5.md` に従って、計画が自前で作る仕組みと、計画が手を入れる箇所に残る自前の仕組みの列挙、および列挙したすべてについて標準の手段・既存依存の機能・定番ライブラリと出典を含める。計画本文から新しく作る仕組みを拾って渡す。工程1の「前提の確認」コメントがあれば、その標準の形が合意済みかも照合できる事実を求める。候補の設計を調査の枠にせず、追加の許可は求めない。

   計画が既存の共用部品（コマンド、公開関数・メソッドなど）の意味（状態遷移・副作用・戻り値の契約）を変える場合、explorer にその部品の全呼び出し元を洗い出し、呼び出し元ごとに前提にしている意味を事実として報告させる。

   修正版計画では、前回の照合後に追加・変更された実装要素、自前の仕組み、および意味の変更が追加・修正された共用部品だけを調べる。既存の仕組みの列挙と標準の手段の調査も、前回から変わった箇所に限る。該当する要素や共用部品が無ければ照合しない。前回の確認後に追加・変更された自前の仕組みが無ければ、工程5の問いに答え直したり、コメントを更新したりしない。

   重複が見つかった場合、または全呼び出し元の照合で計画が触れていない呼び出し元の前提が変更後の意味と食い違うことが分かった場合は、一次評価の見落としとして扱う。修正点は確定しているため、5-[3/3]の規定どおり人間に問わず差し戻す。

   工程5の第1問に仕組みが1つ以上挙がった場合は、`premise-check-stage-5.md` の4問に答える。計画が標準の形を土台にしているかを評価し、結論を選ぶ。`comment-issue.js` でIssueコメントを承認または差し戻しの指示より前に投稿する。冒頭に結論を置き、問いごとに見出しを分け、外部の事実に出典リンクを付ける書式は `premise-check.md` の共通書式と `premise-check-stage-5.md` の「答えを書くIssueコメント」に従う。投稿後、5-[3/3]で人間に問わない場合は、結論とコメントURLを1行で事後報告する。

   第1問に仕組みが挙がらなければ、この問いへのIssueコメントは投稿しない。5-[3/3]で人間に問わない場合は、対象外の根拠を1行で事後報告する。どちらの事後報告も `SKILL.md`「通知と応答」に従い、末尾を「—」にする。

#### 5-[2/3] architect の計画レビューを依頼するか問う【任意】

architect の起動可否は人間が決める（「ワーカーの使い分け」）。5-[1/3]の評価で、設計上の複雑さやリスクが高く architect の計画レビューに価値があると判断した場合だけ、`工程5-[2/3]` と名乗り、理由を添えて「architect に計画レビューを依頼するか」を人間に問う。依頼すると決まったら、`{{SHARED_SKILLS_PATH}}/gh-maestro-orchestrator/architect.md` の「Architect による計画レビュー」に従って起動し、レビュー結果を待ってから5-[3/3]へ進む。

価値が無いと判断した場合は問わず、5-[3/3]へ進む。修正版計画では、architect のレビューで要修正とされた点の修正を確かめる必要がある場合を除き、問わない。

#### 5-[3/3] 承認・差し戻し・人間への問い【必須】

5-[1/3]の評価と、architect のレビューがあればそれも踏まえて orchestrator が評価を決め、次のどれか1つだけを行う。architect の評価は判断材料であり、orchestrator の評価を拘束しない。

- **承認推奨**: 人間に提示も質問もせず、工程6の承認で実装開始を指示する。初回の計画か修正版か、前回の差し戻しを誰が決めたかで区別しない。工程5の問いが「計画のまま進めてよい」と結論した場合も、ほかの評価と合わせて承認を推奨できる。
- **要修正で、修正点が orchestrator 側で確定しているとき**: 人間に問わず、修正点を列挙して工程6の差し戻し（修正依頼）でコーダーへ送る。工程5の問いによる差し戻しでは、標準の置き換え手段が1つに定まり、新しい依存を加えずに済む場合にこの分岐を使う。修正版計画が届いたら工程5をやり直す。
- **要修正で、人間の判断を要する論点が残っているとき**: 複数の置き換え候補がある場合、新しい依存の導入が必要な場合、またはIssueの要件が標準の形とぶつかり見直しが必要な場合は、その論点そのものを人間に問う。Issueの見直しの場合は承認も差し戻しもせず、書き直すか、閉じるか、そのまま続けるかを人間に確認する。回答を得てから差し戻す内容を決める。判断が返らないまま差し戻しても、コーダーへ送る内容が決まらない。

人間に問わない決定の後は、5-[1/3]の定めに従って結論（工程5の問いに該当する場合はコメントURLも）を1行で事後報告する。問いが対象外なら、その根拠を示し、IssueコメントURLは付けない。いずれも末尾は「—」とする。

人間に問うときは次の骨格で状況を示し、「人間への発言の規範」に従って末尾に問いを1つだけ置く（docs/adr/0007-one-question-per-human-message.md）。計画全文を読まなければ答えられない問いにしない。

```
工程5-[3/3] Issue #<N>

コーダー（<coder/senior-coder>）の実装計画:
  <計画コメントURL>

<architectレビューがある場合>
architect の計画レビュー: <承認推奨 or 要修正>
  <レビューコメントURL>
  <要約>

人間の判断を要する論点: <論点と、判断に要る材料>
```
