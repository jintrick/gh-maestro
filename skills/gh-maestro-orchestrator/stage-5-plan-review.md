# 工程 5. 計画評価【必須】

このファイルは、同じIssueを担当するorchestratorが工程5で実行する手順の正本である。工程番号・必須／任意・入口／待機／遷移を確認して進める。人間への発言と工程横断の不変条件はSKILL.mdに従う。

<!-- gh-maestro-structure: middle-items=3 -->

入口: PLAN_REPORTED:<issue>:<planCommentId>を受けたとき。待つもの: 評価に必要な報告。人間の判断を要する論点が残る場合と、architect の計画レビューを問う場合は人間の回答。次: 承認または差し戻しで工程6、更新計画の報告後は工程5を再実行。

計画の承認は orchestrator が持つ。orchestrator が承認推奨と評価した計画は、初回か修正版かを問わず、人間に提示も質問もせず実装を開始する。人間に問うのは、範囲など人間の判断を要する論点が残っているときと、architect の計画レビューを依頼するか決めるときだけである。

中項目の番号は、人間に名乗る場面に振る。5-[1/3]はorchestratorの内部作業である。人間に声をかけるのは、5-[2/3]で問うときと、5-[3/3]で人間の判断を要する論点を問うときだけである。

#### 5-[1/3] 計画の評価【必須】

次を上から順に行う。人間には名乗らない。

- **計画の取得**: 計画URL報告が `msg-poll.js` で分類された `PLAN_REPORTED`を受け取ったら、Issue番号を指定して計画本文を取得する:

   ```sh
   node "{{SCRIPTS_PATH}}/msg-read.js" --plan --issue $ISSUE --workspace $WORKSPACE
   ```

- **orchestrator自身による一次評価**: 計画本文をIssue本文の要件定義と照合し、以下を確認する：
   - 要件定義の全項目が計画でカバーされているか
   - 変更方針・作業分割が要件に対して妥当か
   - 受け入れ条件を満たせそうか
   - 受け入れ条件ごとの「テストが検出すべき欠陥」の欄が計画にあるか。欄が無い場合、または受け入れ条件と対応していない場合は、見落としとして扱う
   - 明らかな見落としやリスクがないか

   **見落としが無ければ「無い」と判定して終える。** 評価した形を整えるために懸念を作らない。実質のない懸念は差し戻しや人間への問いを生み、判断の材料ではなく雑音を増やす。

- **既存パターンの照合**: 計画に含まれる具体的な実装要素（新設する処理・追加するモジュール・採用するアルゴリズム等）について、`gh-maestro-explorer` に類似の既存実装・共有ヘルパーの有無を調査させる。特定の1ファイルを「参考実装」として示させるのではなく、共有ヘルパーの有無を確認させる。計画が既存の共用部品（コマンド、公開関数・メソッドなど）の意味（状態遷移・副作用・戻り値の契約）を変える場合、orchestrator は explorer に、その部品の全呼び出し元を洗い出し、呼び出し元ごとにどんな意味を前提に呼んでいるかを事実として報告させる。重複が見つかった場合、または全呼び出し元の照合で計画が触れていない呼び出し元の前提が変更後の意味と食い違うことが分かった場合は、一次評価の見落としとして扱う。修正点は確定しているため、5-[3/3]の規定どおり人間に問わず差し戻す。修正版計画では、前回の照合後に追加・変更された実装要素、および意味の変更が追加・修正された共用部品だけを照合する。該当する要素や共用部品が無ければ照合しない。

#### 5-[2/3] architect の計画レビューを依頼するか問う【任意】

architect の起動可否は人間が決める（「ワーカーの使い分け」）。5-[1/3]の評価で、設計上の複雑さやリスクが高く architect の計画レビューに価値があると判断した場合だけ、`工程5-[2/3]` と名乗り、理由を添えて「architect に計画レビューを依頼するか」を人間に問う。依頼すると決まったら、`{{SHARED_SKILLS_PATH}}/gh-maestro-orchestrator/architect.md` の「Architect による計画レビュー」に従って起動し、レビュー結果を待ってから5-[3/3]へ進む。

価値が無いと判断した場合は問わず、5-[3/3]へ進む。修正版計画では、architect のレビューで要修正とされた点の修正を確かめる必要がある場合を除き、問わない。

#### 5-[3/3] 承認・差し戻し・人間への問い【必須】

5-[1/3]の評価と、architect のレビューがあればそれも踏まえて orchestrator が評価を決め、次のどれか1つだけを行う。architect の評価は判断材料であり、orchestrator の評価を拘束しない。

- **承認推奨**: 人間に提示も質問もせず、工程6の承認で実装開始を指示する。初回の計画か修正版か、前回の差し戻しを誰が決めたかで区別しない。
- **要修正で、修正点が orchestrator 側で確定しているとき**: 人間に問わず、修正点を列挙して工程6の差し戻し（修正依頼）でコーダーへ送る。修正版計画が届いたら工程5をやり直す。
- **要修正で、範囲など人間の判断を要する論点が残っているとき**: その論点そのものを人間に問う。承認／修正依頼の二択は問わない。回答を得てから差し戻す内容を決める。判断が返らないまま差し戻しても、コーダーへ送る内容が決まらない。

人間に問うときは次の骨格で状況を示し、「人間への発言の規範」に従って末尾に問いを1つだけ置く（docs/adr/0007-one-question-per-human-message.md）。計画全文を読まなければ答えられない問いにしない。

```
工程5-[3/3] Issue #<N>

コーダー（<coder/senior-coder>）の実装計画:
  <計画コメントURL>

<architectレビューがある場合>
architect の計画レビュー: <承認推奨 or 要修正>
  <レビューコメントURL>
  <要約>

人間の判断を要する論点: <論点と、判断に要る材料>
```
