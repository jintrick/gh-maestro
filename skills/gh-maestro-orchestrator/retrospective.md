# 反省会の実施手順

工程9で実施すると決まった後の手順である。分析対象とスキップ判断は工程9に従う。人間への発言はSKILL.mdの「人間への発言の規範」に従う。PR_MERGEDで届くstage-8・stage-9とこのファイルを続けて読む。

## 1. 対象の除外と再発経路

実際に今回のレビューで指摘されなかった予防案、一般論、重大度だけを根拠にした対策、再発する構造的原因を説明できない単発の見落としは提案しない。「本人に注意すれば直る」は使わず、永続化する価値があるかを判断する。指摘ごとに、修正がマージされた後も同じ問題を書ける具体的な経路が残るかを確認する。根拠は元の指摘、PR差分、工程7の修正pushごとのexplorer確認結果。再発経路が無い指摘は提案から外し、理由を「見送った指摘」に記録する。

## 2. 分類と提案

各指摘を次の優先順で分類し、構造的に防げるものを提案する。すべての提案に「入れないと次に何が起きるか」という推奨理由と、修正後に残る再発経路を付ける。理由または再発経路を示せない提案は出さない。

| 優先 | 分類 | 提案先 |
|---|---|---|
| 1 | 型・制御フローで発生を防げる | 該当コードの構造修正Issue。diagnosticianに影響範囲と他の呼び出し経路を調査させる |
| 2 | Lintで検出できる | lint設定の更新Issue |
| 3 | テストで検出できる | 該当テストへの追加Issue |
| 4 | プロジェクト固有で、今回実際に起きた問題に直接対応する | `.claude/rules/` の提案 |
| 5 | 全プロジェクト共通の実装規範 | `gh-maestro-coder` SKILL.md の提案 |
| 6 | 個別判断で汎用化できない | 記録のみ。提案しない |

コードの構造や機械的な検査を優先し、ルールを読んで守ることへの依存は次善策とする。Issueの書き方やコーダーへの伝え方は、上記で防げない場合だけ口頭で付記する。

`.claude/rules/` の提案では、対象プロジェクト、ファイル名、内容、適用根拠、現在の `paths:` を全件記載する。`paths:` は原則必須で、狭く適用する。全ファイル共通とする場合はその根拠を明記し、広いglobや根拠のない省略を提案しない。

## 3. コーダーへの意見聴取

聴取はターンを消費するため、人間の許可なしに行わない。分類の境目で判断が分かれる場合、または原因がIssueの曖昧さ等にありコーダーでないと確認できない場合だけ、質問内容を示して許可を求める。許可されなければ聴取を省略する。それ以外は直接素案作成へ進む。

許可された場合だけ、対象Issueのcoderへ次のように尋ねる。

```sh
node "{{SCRIPTS_PATH}}/msg-send.js" --issue <実装Issue> --skill gh-maestro-coder --workspace $WORKSPACE --stdin <<'EOF'
反省会の分類案です。異論や補足があれば教えてください: <分類案の要約>
EOF
```

返答があれば素案へ反映する。一定時間応答がなくても待ち続けず、先へ進んでよい。

## 4. 素案をIssueに提示する

まず構造化した素案を対象Issueへ投稿し、その後、人間には全文を再掲せず短く通知する。提案が0件でも「改善点なし」と明示した素案を提示し、人間の返答を待つ。返答前に後始末やIssueクローズへ進まない。

素案の形式:

```md
【反省会】Issue #<N> / PR #<PR>

## 型・制御フローで防止
- <指摘> → <構造修正案>（推奨理由: <次に起きること>）
  - 修正後に残る再発経路: <具体的な箇所・経路>
  - 既存コードへの影響: 承認後に調査
## Lintで検出
- <指摘> → <ルール案>（推奨理由: <次に起きること>）
  - 修正後に残る再発経路: <具体的な箇所・経路>
  - 既存コードへの影響: 承認後に調査
## テストで検出
- <指摘> → <テスト案>（推奨理由: <次に起きること>）
  - 修正後に残る再発経路: <具体的な箇所・経路>
  - 既存コードへの影響: 承認後に調査
## .claude/rules/化
- <指摘> → <ファイル名・記述案・適用根拠>（推奨理由: <次に起きること>）
  - 現在の paths: <全件、または「未設定」>
  - 修正後に残る再発経路: <具体的な箇所・経路>
## coder SKILL.md への追加
- <指摘> → <追記案>（推奨理由: <次に起きること>）
  - 修正後に残る再発経路: <具体的な箇所・経路>
## 見送った指摘
- <指摘> → <再発経路が残らない根拠>
## 今回限りの個別判断
- <汎用化できない内容、または「なし」>

提案がない分類には「なし」と記載する。

---
上記の改善を実施しますか？
```

投稿は `write-draft.js` で本文を `/tmp/retro-<N>.md` に書き、`comment-issue.js` に渡す。

```sh
node "{{SCRIPTS_PATH}}/write-draft.js" /tmp/retro-<N>.md --stdin <<'EOF'
<素案>
EOF
node "{{SCRIPTS_PATH}}/comment-issue.js" --issue <N> --repo $REPO --workspace $WORKSPACE --body-file /tmp/retro-<N>.md
```

投稿成功後の人間向け通知は「【反省会】Issue #<N> に素案を投稿しました。ご意見をお願いします。」とする。GitHub上のIssueコメントはassistantも参照できる。

## 5. 人間の判断後

人間の返答を受け取るまで待つ。承認された項目だけを実施し、却下・保留も決定事項に残す。

- 構造修正・Lint・テストの提案: diagnosticianに既存違反の件数と改修範囲を調査させてからIssueを起票する。規模が大きければ起票せず、人間に再判断を求める。
- `.claude/rules/` の追加: 内容を人間に提示して承認を得てから対象プロジェクトへ反映する。承認後は許可された例外に従いBASE_BRANCHへ直接commit/pushし、`git show --stat` で対象だけを確認する。
- coder SKILL.md の更新: 内容を人間に提示して承認を得てから反映する。

最後に、承認・却下・保留と反映先を次の決定事項本文へまとめる。本文ファイルは `/tmp/retro-decision-<N>.md` に作成し、`stage-9` の finalize-issue.js 呼び出しへ渡す。ここでは別途コメント投稿しない（二重投稿防止）。人間がまだ返答していない、または承認された対応が未完了なら finalize しない。

```md
【反省会】決定事項 Issue #<N> / PR #<PR>

| 指摘 | 分類 | 決定 | 反映先 |
|---|---|---|---|
| <指摘内容> | <分類> | 承認／却下／保留 | Issue #<M>／.claude/rules/<file>／SKILL.md<節>／対応なし |
```
