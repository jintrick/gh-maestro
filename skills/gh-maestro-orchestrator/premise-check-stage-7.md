# 前提を疑う問い — 工程7: レビュー指摘のトリアージ（参照専用）

共通の定義は `premise-check.md`、トリアージの手順は `triage.md` にある。

## 疑いを向ける場面

トリアージで、推奨が「コーダーに修正依頼」か「保留Issueに積む」で、かつ次のどちらかに当たる指摘を対象にする。無視を推奨する指摘は対象外。当たるかは orchestrator が指摘の本文から判定し、対象のコードは読まない。

- 指摘が突く仕組みが、`premise-check.md` の「疑う対象の仕組み」（汎用的な仕組み、またはセキュリティに関わる仕組み）に当たる。
- 同じ仕組みへの指摘が続いている（同じ PR の再レビューで繰り返される、または直近の Issue でその仕組みの手直しが続いている）。

## 材料の出どころと explorer への依頼

- **突いている仕組みの自前の部分**: 指摘の本文から読む。指摘は Review Manager がコードを読んで書いたもので、対象のファイル:行と確かめた参照を持つ。
- **代わりになる標準の手段**: まず同じ Issue の工程1「前提の確認」と工程5「計画の形の確認」のコメントから取る。指摘が突く仕組みはこの PR の計画で作った・触ったものが多く、そこで既に標準の手段を出典付きで調べている。
- どちらのコメントにも無い仕組みのときだけ、トリアージの表を出す前に、その Issue の explorer に1回依頼する。許可は求めない（工程5と同じ扱い）。該当する指摘をまとめて渡し、仕組みの自前の部分（ファイル:行）と、代わりになる標準の手段と出典を、事実として集めさせる。どちらの対策がよいか、修正の方針は求めない。

## 4つの問い

対象の指摘ごとに orchestrator が答える。

1. **突いている仕組み**: 指摘が突いているのは、どの仕組みのどの自前の部分か。
2. **代わりになる標準の手段**: 既存の依存の機能や定番のライブラリで代わりになるものはあるか。出典を付ける。工程1・5の確認コメントがあれば、そこで合意した標準の形に含まれるかも示す。
3. **対策の比較**: 指摘の方向どおりに直した場合に何が残るか。標準の手段に置き換えた場合に何が消え、何がかかるか（新しい依存、Issue の範囲を越えるか）。
4. **推奨**: 理由とともに次の1つを選ぶ。どれにするかは人間が決める。
   - 指摘の方向どおりに直す
   - 標準の手段に置き換えて直す
   - 今回は指摘の方向どおりに直し、置き換えは保留Issueに積む

## 答えを書くIssueコメント

場面に当たる指摘が1件以上あれば、トリアージの表を出す前に、答えを `comment-issue.js` で Issue コメントに投稿する。1回のトリアージで対象が複数あれば1件にまとめ、指摘ごとに節を分ける。冒頭に結論を置き、指摘ごとの節、4つの問いごとの見出しを分け、外部の事実には出典リンクを付ける。当たる指摘が無ければ投稿しない。
