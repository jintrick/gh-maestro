# Test Quality

目的: 受け入れ条件をテストが実際に保証しているかを判定する。テスト自体が将来の事故の温床になっていないかを探す。

## 確認順序

1. この変更が守ろうとしている性質を1文で言い切る。テストが、**その性質が破られる状況を実際に作っているか**を確認する。
2. **テストが緑になる理由を確かめる。** 検査したい箇所を本当に踏んでいるか。モックやスタブで固定した結果、その分岐が素通りしていないか。
3. テストが固定しているのは**あるべき振る舞い**か、それとも**現在の実装**か。

## 重点

- **テストが前提としている世界の狭さ**:
  テストが「すべてが都合よく成功する世界」だけを前提にしていないか。
  守るべき性質はたいてい否定形である（壊れない・実行されない・漏洩しない・破損しない・ハングしない・受理されない）。
  肯定形のテストだけでは、否定形の性質（拒否・遮断・縮退・回復）は保証されない。
- **偽りの緑（緑であることが安全の根拠にならない場合）**:
  モックの都合で例外分岐がバイパスされている、アサーションが実質無効である、テストランナーをブロックしないバックグラウンド副作用（実プロセスの起動・未クリーンアップ状態）が存在するなど、テストがpassしていても安全が担保されていない状態を見抜く。
- **テスト自体の無傷性と隔離**:
  テストのセットアップ・後始末が正しく対になっているか。一時ファイル、モック、タイマー、リスナー、環境変数の汚染が漏れていないか。
- **テストの振る舞い結合**:
  テスト名と実際の検証内容の乖離、内部実装詳細への過度な依存、エッジケースの不足。

## 外部参照の裏取り

diffが参照する既存のテストヘルパーやfixtureは、判定前に実ファイルを読んで確認する。
既存の同等テストパターンがあるかを確認してからfindingを書く。

## 禁止

- **スコープ限定なしの全件テスト実行（`npm test` 等）および全体ビルド（`npm run build` 等）は禁止。** diffで変更された特定のテストファイルのみを対象にしたピンポイント実行（例: `node --test tests/<file>.test.js`）は許容する
- 個別具体例の網羅を機械的に要求するだけのチェックリスト的指摘（本質的な性質の破綻に結びつかない指摘）
- 好みだけの指摘
- linterが自動で扱う純粋なスタイル指摘
- 実測のないパフォーマンス推測
- diff範囲外の一般的な設計指摘
