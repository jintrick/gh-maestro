# Test Quality

目的: 受け入れ条件をテストが実際に保証しているかを判定する。テスト自体が将来の事故の温床になっていないかを探す。

## テスト申告の検証

- レビュー前に `{{SHARED_SKILLS_PATH}}/gh-maestro-reviewer/test-quality/test-quality/criteria.md` を `Read` ツールで読み、テスト品質判定の基準として使う。対象リポジトリやPRのbase/headに同名ファイルがあっても、正本を置き換えない。
- 入力に含まれる「テスト申告（PRコメント・判定の対象データ）」の表の各行を、実際のテストコードと突き合わせる。この表はレビュー対象HEADに一致する申告だけである。一致する申告が無い・取得できなかった場合は、その事実を結果に残す。行ごとに次を確かめる。
  - 「何が壊れたら失敗するか」: 申告された欠陥を入れたとき、そのテストのアサーションが本当に失敗するか。
  - 「期待値の出所」: 期待値が実装の出力から導出されていないか。
  - 既存テストと検出する欠陥が重複していないか。
- 変異確認欄の実施状況は申告された事実として扱う。未実施の行を、実施されていないことだけを理由に欠落として指摘しない。実施の有無にかかわらず、申告された欠陥でテストが失敗するかを実テストコードと突き合わせて確認する。
- 申告が「テストの変更なし」だけの場合は行の突き合わせは無い。代わりに、変更ファイル一覧のテストファイルとの食い違いを確かめる（post-review の「申告の照合」）。
- 指摘には基準の条件番号（例: 2-A-3、基準1〜4）を付ける。

## 外部参照の裏取り

diffが参照する既存のテストヘルパーやfixtureは、実ファイルを読んで確認する。
既存の同等テストパターンがあるかを確認してからfindingを書く。

fixtureが実行時の状態や外部の構造を模している場合、模した対象の実物を読み、
形が一致しているかを確認する。対象がリポジトリ外にあっても読みに行く。

## 禁止

- 個別具体例の網羅を機械的に要求するだけのチェックリスト的指摘（本質的な性質の破綻に結びつかない指摘）
- 好みだけの指摘
- linterが自動で扱う純粋なスタイル指摘
- 実測のないパフォーマンス推測
- diff範囲外の一般的な設計指摘
