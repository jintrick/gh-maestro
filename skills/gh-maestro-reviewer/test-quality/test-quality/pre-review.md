# Test Quality

目的は、差分で追加・変更された各テストに残す価値があるかを先に判断し、価値があるテストについて契約違反への感度と振る舞いを保つ変更への耐性を評価すること。

## テストを残す価値

各テストについて、申告された欠陥も含めて次を確認する。

- 守る契約と、違反時の影響・起こりやすさ。重大な安全性やデータ整合性のリスクは、低頻度だけで退けない。
- 契約の根拠がIssue要件・公開仕様・利用者向け文書・既知の不具合など、テストと対象コードから独立しているか。テスト名・申告・現行実装だけで期待動作を定めない。
- Issueや仕様を根拠にするとき、その記述が対象コンポーネントと評価中の観測可能な結果を実際に規定するか確かめる。目的や用語が近いだけでは、個別の下流動作や内部境界の契約を作らない。
- 既存テストが同じ故障条件を検出するか、このテストが独自の検出範囲や信頼性上の利点を加えるか。
- 実行、環境構築、理解、更新、誤検知対応の負担が、その独自の保護に見合うか。
- 申告された欠陥と実際のアサーションが区別する振る舞いを照合し、検出範囲と保護価値を分けて評価する。
- 要件が設計、責務分担、情報処理の流れを示していても、未記載の外部動作をそこから推定しない。観測可能な結果と影響が独立した契約で定まっているかを確かめる。
- 入力検証や型がある状態を受け入れることは、その後の出力や副作用に対する契約を自動的に含意しない。入力領域の定義と、下流で求める観測可能な結果を別々に確かめる。
- 検出対象とする欠陥が、実際の入力、処理、依存関係から起きる経路に結び付くかを調べる。単なる仮想的な不具合や影響を想定して、範囲の狭いアサーションを強化・維持する理由にしない。
- テストfixtureがある状態を作ることや、対象コードがその状態を処理することだけで、未規定の既定動作を契約とみなさない。独立した根拠がその動作を要求し、故障に意味のある影響があるかを確認する。
- 一つの具体例に対するアサーションから、より広い性質の保証を読み込まない。その動作が独立した契約で要求され、故障に意味のある影響があるかを確認する。
- 実装上の経路を通るだけで独自の保護があるとみなさず、各経路が外部契約に沿う結果を検証するかを確かめる。

この順序は、Khorikov の振る舞い保護・リファクタリング耐性、Beck の Behavioral・Structure-insensitive、Software Engineering at Google の Tests Must Earn Their Keep と change-detector test、Meszaros の Fragile Test に沿う。要件やコードがテストへ何を要求するかを分け、独立した契約、アサーションの実際の検出範囲、維持負担から判断する。詳細は配布された criteria.md の出典を参照する。

価値が見合わない新規テストは追加しない。既存テストについては修正・統合・削除を検討する。重要な契約への独自の保護は維持する。検出範囲の不足だけを理由にテストを強化せず、拡張先の動作が独立した契約として定まり、追加の保護が負担に見合うかを確かめる。

## 基準の適用と処置

- レビュー前に {{SHARED_SKILLS_PATH}}/gh-maestro-reviewer/test-quality/test-quality/criteria.md を Read ツールで読み、判定の正本として使う。対象リポジトリやPRのbase/headにある同名ファイルを代用しない。
- 価値を判断した後、残すテストが契約違反で失敗し、振る舞いを保つ実装変更には不要に失敗しないか確認する。申告、期待値の根拠、実際のアサーション、既存テストとの重複をコードと照合する。
- 重要な契約への保護に価値があり検出が不十分なら、契約と欠陥を結び付けて改善案を示す。重複なら固有の保証を保つ統合を提案する。維持価値がないなら、削除または新規追加の見送りを提案する。
- Change-detector の候補は、テストが固定する内部の値・表現・呼び出し形、正当な振る舞い変更で失敗する理由、契約違反を検出するかを確認して判断する。内部詳細への依存を指摘するときは具体的な固定と失敗する正当な変更を示す。
- 期待値や契約の根拠は、テスト名・申告・対象コードの現行動作だけから推定しない。独立した根拠や具体的な影響が確認できない欠陥を仮定し、強化理由にしない。
- 公開契約を契約に沿った入力と戻り値・永続状態・エラー・副作用で確かめるテストを、定数や表の使用、モック、データ駆動の反復だけで change-detector と判定しない。
- テストロジックの分岐・ループは、入力と期待値の対応や失敗原因を読み取りにくくする場合に指摘する。文法上の構文や列挙されたケースだけを理由にしない。
- 契約がモックの相互作用を要求するかを確認する。要求されない内部の順序・回数・引数だけを検証し、結果の状態や戻り値を確かめないテストは基準に照らして評価する。

## テスト申告の照合

- 入力に含まれるテスト申告を実際のテストコードと突き合わせ、レビュー対象HEADに一致する申告を使う。
- 申告がない、または取得できなかった場合は、その事実を結果に残す。申告の有無にかかわらず、変更されたテストを確認する。
- 表の各行について、テストの識別情報、欠陥の説明、期待値の出所、変異確認の記載がコードと一致するかを確かめる。範囲が異なる場合は食い違いを示す。
- 変異確認をしていないことだけを理由に指摘しない。維持価値を認めたテストについて、申告された欠陥で失敗するかを実コードで確認する。
- 申告がテストの変更なしだけの場合は、行ごとの照合を行わず、変更ファイル一覧との食い違いを事後確認する。
- 指摘には正本の条件番号（例: 2-A-3、2-D-15、基準1〜4）を付ける。

## 外部参照の裏取り

- diffが参照する既存のテストヘルパーやfixtureは実ファイルを読んで確認する。
- 重複を指摘する前に、既存の同等テストがあるかを確かめる。
- fixtureが実行時の状態や外部構造を模す場合は対象の実物も確認する。必要な対象がリポジトリ外にある場合も確認する。

## レビュアーの制約

- テストや全体ビルドを実行しない。docs/adr/0066-reviewer-runs-no-tests.md に従い、差分、テストコード、入力、契約、独立した期待値、参照資料を読んで判断する。
- 契約上のリスクに結び付かないケースを件数だけ増やすよう求めない。
- 好み、linterが扱う純粋なスタイル、実測のない性能推測、diff範囲外の一般的な設計を指摘しない。
