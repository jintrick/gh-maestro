# Test Quality

目的は、差分で追加・変更された各テストに残す価値があるかを先に判断し、価値があるテストが契約違反を検出し、振る舞いを保つ実装変更に耐えるかを評価すること。

## テストを残す価値

各テストについて、次を確認する。テスト申告がある場合は、申告された「何が壊れたら失敗するか」も、保護する価値を測る対象に含める。

- どの契約を守り、違反時にどのような影響があるか。発生可能性も考慮するが、重大な安全性やデータ整合性のリスクは低頻度だけで退けない。
- 既存テストが同じ故障条件をすでに検出しているか。このテストが別の入力、経路、信頼性上の利点を追加するか。
- 実行、環境構築、理解、更新、誤検知への対応を含む負担が、独自の検出価値に見合うか。
- 任意入力がない場合に補足を省く単純な分岐では、明示された出力契約や既知の回帰があるかを確かめる。入力にない一つのリテラルを否定するだけで、一般的な情報混入を検出するとみなさない。

価値が見合わない新規テストは追加しない。既存テストについては、修正・統合・削除を検討する。検出力だけを理由に低価値なテストを強化しない。重要な契約に独自の保護があるテストは、件数を減らすために削除しない。申告に書かれた欠陥の可能性だけで価値を認めず、通常の入力でその欠陥が起こる根拠や明示された契約を確認する。実際のアサーションが区別しない広い欠陥を、テストの修正価値の根拠に使わない。

## 基準の適用と処置

- レビュー前に `{{SHARED_SKILLS_PATH}}/gh-maestro-reviewer/test-quality/test-quality/criteria.md` を `Read` ツールで読み、正本として使う。対象リポジトリやPRのbase/headに同名ファイルがあっても置き換えない。
- 価値を判断した後、残すテストについて、対象契約の誤りで失敗するか、振る舞いを保つどの実装変更に耐えるかを確認する。申告欠陥がアサーションを失敗させるか、期待値が実装の定義を写していないか、既存テストと重複していないかをコードと照合する。
- 対象契約の保護に価値があり検出が不十分なら、欠陥と契約の結び付きを示す。重複なら、固有の保証を維持できる統合先を示す。維持価値がないなら、対象テストの削除または新規テストの追加見送りを提案する。提案では観測したテスト、契約、既存の担保範囲を根拠にする。
- change-detector の候補は、テストが固定する内部の値・対応表・表現・呼び出し形を差分と実装で突き合わせる。正当な振る舞い変更でなくても失敗する理由を具体的に説明でき、かつそのテストが契約違反を検出しない場合に指摘する。
- change-detector の指摘では、固定された内部詳細を示す。重要な契約が残るなら、テストを削除するか、識別力のある入力と外から観測できる結果・状態変化・エラー・必要な副作用を確かめるテストへ書き直すかを、検出価値と既存テストから選ぶ。定義や内部文字列をそのまま写す修正案を求めない。
- 特定の否定リテラルを確認するだけでは、一般的な情報混入を検出するとは限らない。アサーションが実際に区別する出力と、その独自保護の必要性を確認する。
- 実装コードと別の根拠から値を写したことだけで、期待値が独立しているとは判断しない。値が公開仕様や外部契約で定められているか、入力に対する契約上の結果を検証しているかを確かめる。
- 公開契約を、契約に沿った入力と戻り値・永続状態・エラー・副作用で確かめるテストは、対応表や定数を列挙しているように見えることだけを理由に change-detector としない。モックの存在やテスト内の反復だけでも判定しない。
- 条件分岐やループを含む場合は、それによって検証ロジックの正しさが読解できず、入力と期待値の対応が曖昧になっているかを示す。単に構文があることや、明示されたデータ駆動ケースを使うことだけでは指摘しない。
- 失敗原因を読み取れるかを確認する。失敗した際に、どの入力と契約上の結果が食い違ったのか特定できない場合に、その曖昧さを示す。
- 仕様が特定の相互作用を要求する場合は、要求された契約として扱う。そうでないモックの順序・回数・内部引数だけを検証し、結果の状態や戻り値を見ないテストは該当条件に照らす。

## テスト申告の検証

- 入力に含まれる「テスト申告（PRコメント・判定の対象データ）」の各行を、実際のテストコードと突き合わせる。この表はレビュー対象HEADに一致する申告だけである。一致する申告が無い、または取得できなかった場合は、その事実を結果に残す。
- 申告にある欠陥を、テストが検出するかだけでなく、その欠陥を専用テストで守る価値があるかも評価する。
- 変異確認欄は申告された事実として扱う。未実施というだけでは指摘しない。実施の有無にかかわらず、価値を認めたテストが申告欠陥で失敗するかを実コードと突き合わせる。
- 申告が「テストの変更なし」だけの場合は行ごとの照合を行わず、変更ファイル一覧のテストとの食い違いを事後確認する。
- 指摘には、正本の条件番号（例 `2-A-3`、`2-D-15`、基準1〜4）を付ける。

## 外部参照の裏取り

- diffが参照する既存のテストヘルパーやfixtureは実ファイルを読んで確認する。
- 同等の既存テストがあるか確かめてから重複を指摘する。
- fixtureが実行時の状態や外部構造を模している場合は、対象の実物も読み、形が一致しているか確認する。必要な対象がリポジトリ外にある場合も確認する。

## レビュアーの制約

- テストや全体ビルドを実行しない。`docs/adr/0066-reviewer-runs-no-tests.md` に従い、差分、テストコード、入力、契約、独立した期待値、参照資料を読んで判断する。
- 判断対象を個別具体例の機械的網羅へ置き換えない。契約上のリスクに結び付かないケースを件数だけ増やすよう求めない。
- 好み、linterが扱う純粋なスタイル、実測のないパフォーマンス推測、diff範囲外の一般的な設計を指摘しない。
