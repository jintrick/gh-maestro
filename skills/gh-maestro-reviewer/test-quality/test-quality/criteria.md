# gh-maestro テスト品質判定基準

## 1. 基本原則

良いテストには、互いに対等な二つの軸がある。

- **振る舞いへの感度**。契約に反する振る舞いの誤りがあれば失敗する。これは Khorikov の「退行からの保護」と Beck の「Behavioral」に対応する。[Khorikov 第4章](https://www.manning.com/books/unit-testing) · [Test Desiderata](https://testdesiderata.com/)
- **振る舞いを保つ変更への耐性**。外から見える振る舞いが同じまま実装の構造を変えても成功する。これは Khorikov の「リファクタリングへの耐性」と Beck の「Structure-insensitive」に対応する。[Khorikov 第4章](https://www.manning.com/books/unit-testing) · [Test Desiderata](https://testdesiderata.com/)

どちらか片方だけではテストの価値を示せない。内部構造が変わるたびに失敗するテストは、正しい変更も妨げてテスト結果への信頼を損なう。構造変更に耐えても、契約違反を見逃すテストは欠陥から守らない。Khorikov はこの二つをテスト価値の主要な属性として説明し、Beck は振る舞いの変化への感度と構造変更への鈍感さを別の望ましい性質として挙げている。

テストは対象の契約を検証する。契約には、公開 API の戻り値、利用者から観測できる状態変化、要求されるエラーや副作用、安全性・性能などの要件を含む。仕様が明示的に保証する呼び出しや値も検証してよい。

テスト件数、コードカバレッジ、アサーション数、成功率の増加を目的化しない。テストを追加しないことも、適切な技術的判断である。

## 2. 不要または有害なテストの判定条件

以下に該当するテストは、原則として新たに作成しない。既存テストについても、修正・統合・削除を検討する。各条件は、対象の契約と差分の意味を確かめて適用する。

### A. 欠陥検出能力の欠如

1. **検出対象が不明確**
   - どの契約違反や不具合を検出するのか説明できない。
   - 何が壊れたら失敗するのか特定できない。

2. **意味のある検証が存在しない**
   - 処理を呼び出すだけで、必要な結果を検証していない。
   - 正常な動作と誤った動作を区別できない。
   - 起動失敗やクラッシュを検出するスモークテストは例外とする。

3. **期待値が実装に従属している**
   - 実装コードや実行結果から期待値を導出している。
   - 現在の実装を無条件に正解として扱い、実装の誤りを追認する。

4. **テスト対象を実質的に検証していない**
   - 検証すべきロジック自体をモック化している。
   - モックに設定した戻り値を確認するだけになっている。
   - 実際の処理に欠陥があっても検出できない。

5. **実装と同一の誤りを共有する**
   - 実装と同じアルゴリズムや同じ誤解を使って期待値を算出している。
   - 独立した正解、契約、または不変条件による検証がない。

### B. 重複と費用対効果

6. **既存テストと実質的に重複している**
   - 既存テストと同じ欠陥しか検出できず、新しい検証条件を加えない。

7. **自明な動作だけを検証している**
   - 言語やフレームワーク自体が保証する動作を再検証している。
   - 独自ロジックのない単純な処理で、重要な契約や回帰リスクにも結び付かない。

8. **内部実装に過度に依存している**
   - 契約で保証されない内部関数の呼び出し回数や処理順序を検証する。
   - 内部データ構造や実装配置の変更で失敗し、外から観測できる振る舞いや必要な不変条件を検証していない。

9. **保守コストが検出価値を上回る**
   - 軽微な実装変更のたびに修正が必要になる。
   - 実行時間や環境構築の負担に見合う独自の欠陥検出能力がない。

10. **カバレッジや件数の増加だけを目的としている**
    - コードを通過させることやテスト数を増やすこと以外の価値を説明できない。

### C. 信頼性と契約との整合性

11. **契約が求めていない動作を固定している**
    - 偶然の実装結果を仕様として扱う。
    - 要件にない制約を追加し、正当な仕様変更やリファクタリングを妨げる。

12. **失敗を隠蔽している**
    - 例外を握りつぶして成功する。
    - エラーや不正な結果を無視する、または成功条件が緩すぎて想定する不具合を検出できない。

13. **合理的な再現性がない**
    - 時刻、乱数、不要な外部環境への依存により結果が不安定になる。
    - 失敗原因を特定できず、信頼できる検証手段にならない。

14. **根拠なく失敗を成功へ変えている**
    - テスト失敗の原因を調査せず、実装結果に期待値を合わせる。
    - 契約上の根拠なくアサーションを削除・弱体化し、本来検出すべき不具合を正常扱いにする。

### D. 変更耐性と読み取りやすさ

15. **Change-detector（変更検知テスト）になっている**
    - 実装の書き方や内部表現を固定するため、外から見える振る舞いを保つ変更で失敗する。
    - テストの期待値が実装の定義から写されているため、対応する振る舞いの誤りを検出できない。
    - 例には、内部の定義表・対応表、選択肢や定数の一覧、内部文字列、文書の文言を実装からテストへ写すことや、契約にないモック呼び出し順序・回数を固定することがある。
    - この条件は Google の Change-Detector Tests と、Meszaros の Fragile Test / Overspecified Software が扱う問題に対応する。[Google Testing Blog](https://testing.googleblog.com/2015/01/testing-on-toilet-change-detector-tests.html) · [xUnit Test Patterns](http://xunitpatterns.com/)

16. **契約にないモック相互作用だけを検証している**
    - 呼び出し順序、回数、内部引数などをモックで固定する一方、利用者に見える戻り値や結果の状態を確かめていない。
    - その相互作用が公開契約や重要な副作用の要件である場合は、この条件に該当しない。[Software Engineering at Google 第12章](https://abseil.io/resources/swe-book/html/ch12.html) · [第13章](https://abseil.io/resources/swe-book/html/ch13.html) · [Khorikov 第5章](https://www.manning.com/books/unit-testing)

17. **テスト自身の分岐やループを読まないと判定できない**
    - 条件分岐やループによって、どの検証がいつ実行されるかをテストごとに確かめにくくしている。
    - 複雑なテストロジックが正しさの根拠になり、入力と期待する振る舞いを直接読めない。
    - データ駆動テストの反復そのものや、明確に列挙された複数ケースだけを理由に指摘しない。[Meszaros, Conditional Test Logic](http://xunitpatterns.com/Conditional%20Test%20Logic.html)

18. **失敗から壊れた振る舞いを特定できない**
    - 失敗したときに、どの入力と契約上の結果が食い違ったのかを読み取れない。
    - 一つのテストが無関係な多数の条件を検証し、どの条件が失敗したか分からない。[Test Desiderata, Specific](https://testdesiderata.com/) · [Meszaros, Assertion Roulette](http://xunitpatterns.com/Assertion%20Roulette.html)

これらの条件は、Khorikov の退行保護・リファクタリング耐性・迅速なフィードバック・保守性、Beck の Behavioral・Structure-insensitive・Fast・Readable・Specific、および Meszaros の Conditional Test Logic・Assertion Roulette などの test smell を、レビューで確認できる判定へ落としたものである。

## 3. gh-maestro 新規テスト採用基準

新規テストは、以下の4条件をすべて満たす場合に採用する。

### 基準1：検証目的が明確

- 対象となる仕様・不変条件・回帰不具合が明確である。
- 想定する故障や誤動作と、失敗する理由を具体的に説明できる。

### 基準2：期待値が独立している

- 期待値に仕様、要件、既知の正解、または外部契約などの根拠がある。
- 独立性とは、実装の定義をテスト側へコピーすることではない。入力に対する外から観測できる出力、状態変化、エラーを、実装とは別の根拠で確かめることである。
- 実装と同じ誤りを共有する危険が考慮されている。

### 基準3：契約違反を検出できる

- 想定する不具合が起きた場合に失敗する合理的な根拠がある。
- 検証対象の処理を実行し、その実際の振る舞いを観測する。
- モックや例外処理によって欠陥を隠蔽しない。

必要に応じてミューテーション確認などで検出能力を確かめる。ただし、すべてのテストに義務付けない。実施範囲は `docs/adr/0060-mutation-check-scope-limited.md` に従う。

### 基準4：追加する価値がある

- 既存テストで十分に検証されていない独自の検出能力、または合理的な検証上の利点がある。
- 外から見える振る舞いが同じまま内部構造や実装表現を変えても、正当な理由なく失敗しない。
- 期待する保護に対して、実行時間、環境依存性、理解や保守の負担が見合う。

**4条件のいずれかを満たさない新規テストは、原則として作成しない。**

## 4. 判定時の境界

- 起動失敗やクラッシュを検出するスモークテストには価値がある。
- モックの使用自体は問題ではない。検証対象のロジックを実行し、外部依存を隔離するためのモックは有効である。
- 戻り値、保存後の状態、利用者から観測できるエラーや副作用を検証するテストは、入力が仕様に沿い、期待値が独立していれば振る舞いを検証している。
- 契約が特定の順序、呼び出し回数、選択肢、定数、メッセージを利用者への約束として明示するなら、その契約を確かめてよい。実装ソースから値や文言を写したというだけでは、独立した期待値にならない。
- 定義表、選択肢一覧、内部文字列、文書文言がテストに現れるだけで change-detector と判定しない。契約上の根拠、テストが与える入力、外から観測する結果を確認する。
- テストにモックがあるだけで、相互作用テストや change-detector と判定しない。何を契約として検証するのか、相互作用以外に何を観測しているかを確認する。
- 条件分岐やループがテストコードにあるだけで指摘しない。読解を妨げるテスト独自の複雑な判定ロジックが、検証の正しさや失敗原因を不明瞭にしているかを示す。
- 正常系・境界値・異常系は、同じ対象でも検出する欠陥が異なれば重複とはみなさない。
- 内部動作の検証でも、重要な不変条件、安全性、性能、または明記された副作用の契約に必要なら有効である。
- 不安定さだけを理由に、必要な統合テストや耐障害性テストを不要とは判断しない。
- 仕様の変更が正当に確認された場合は、根拠に合わせて期待値を更新してよい。
- テストの削減自体を目的化しない。有効なテストを数合わせで削除してはならない。
- Test Quality レビューはテストを実行しない。判断は差分、コード、入力、独立した期待値、参照資料を読んで行う。`docs/adr/0066-reviewer-runs-no-tests.md` に従う。

## 5. gh-maestro 固有のレビュー条件

外部のテスト品質原則に加え、次の gh-maestro 固有の確認を維持する。

- 申告の欠陥、期待値の出所、変異確認の申告を実際のテストコードと照合する。変異確認をしていない事実だけでは指摘しない。`docs/adr/0051-test-quality-by-declaration-and-verification.md` と `docs/adr/0060-mutation-check-scope-limited.md` に従う。
- テスト層が分かれている場合は、差分の各テスト関数が適切な層に置かれているか確認する。
- テストが前提とする入力の形、成功時だけを想定した経路、隔離と後始末を確認する。
- 監視ペインなど人が目で判断する表示の見た目を固定するテストを指摘するときは、`docs/adr/0033-do-not-pin-rendered-appearance-in-tests.md` の境界を守る。画面から分からない状態や関係の検証は維持する。
- 好み、純粋なスタイル、実測のない性能推測、差分範囲外の設計を指摘しない。

## 6. 最終判断

テストごとに二つの問いへ答える。

1. **契約に反するどの振る舞いが起きたら失敗するか。**
2. **振る舞いを保つどの実装変更では成功し続けるか。**

どちらかを具体的に説明できない場合は、そのテストの検出価値、期待値の根拠、内部構造への依存を見直す。change-detector の問題を指摘するときは、該当する内部の固定と、テストが代わりに確認すべき入力および観測可能な結果を示す。
