# Test Quality — 事後確認

指摘を書き終えてから、この表を使って担当観点の取りこぼしと誤指摘を確認する。各テストの要否を検出力より先に評価し、基準番号の意味は事前に読んだ配布正本に従う。

## テストを残す価値

- 追加・変更された各テストが守る契約、違反時の影響・起こりやすさ、申告された欠陥の保護価値を確認したか。
- 契約の根拠が、テスト名・申告・対象コードの現行動作だけに依存していないか。Issue要件・公開仕様・利用者向け文書・既知の不具合など独立した根拠を確認したか。
- Issueや仕様を根拠にするとき、その記述が対象コンポーネントと評価中の観測可能な結果を実際に規定するか確かめたか。目的や用語の近さだけで契約の範囲を広げていないか。
- 設計や情報処理の流れに関する記述だけから、未記載の外部動作を契約として補っていないか。利用者に見える結果と影響が、独立した根拠で定まっているか。
- 入力検証や型がある状態を受け入れることだけで、下流の結果を契約とみなしていないか。入力領域の定義と、外部に求める結果を分けて確認したか。
- 検出対象の欠陥が実際の入力・処理・依存関係から起きる経路に結び付いているか。単なる仮想的な不具合や影響を狭いアサーションの強化・維持理由にしていないか。
- テストfixtureがある状態を作ることや、対象コードがその状態を処理することだけで、未規定の既定動作を契約とみなしていないか。独立した根拠と故障時の影響を確認したか。
- 一つの具体例に対するアサーションから、より広い性質の保証を読み込んでいないか。その動作が独立した契約で要求され、故障に意味のある影響があるか確認したか。
- 既存テストが同じ故障条件を検出していないか調べ、対象テストの独自の検出範囲を確認したか。
- 実行、環境依存、理解、更新、誤検知対応の負担と、独自の保護が見合うかを判断したか。
- 申告された欠陥と実際のアサーションが区別する振る舞いを照合し、検出範囲と保護価値を分けたか。アサーションが検出しない広い欠陥を価値や強化の根拠にしていないか。
- 実装上の経路を通るだけで独自の保護があるとみなさず、経路が外部契約に沿う結果を検証するか確認したか。
- 検出範囲の拡張を提案する前に、拡張先の振る舞いが独立した契約として示され、追加の保護が負担に見合うかを確かめたか。
- 削除・統合を提案する場合、観測した重複または廃止契約を特定したか。重要な契約を唯一守るテストを削除せず、統合後も固有の保証が残るか確認したか。
- 有効なテストを件数やカバレッジの増減だけを理由に追加・削除する提案をしていないか。

## 申告の照合

- 追加・書き直されたテストのうち、入力のテスト申告に行がないものを確認する。申告が無い、または取得できなかった事実はその旨を結果に残す。
- 申告表の各行と実テストの中身が食い違っていないか確認する。テストの識別情報、申告された欠陥、期待値の出所、検証内容のずれを指摘する。
- 複数の行で同じ申告文を使い回していないか確認する。
- 申告がテストの変更なしなのに変更ファイル一覧にテストがある場合、または表にテストがあるのに変更一覧に該当テストがない場合は食い違いを示す。テストかどうかは入力の変更ファイル一覧と基準の判定対象（tests/**）に従う。
- 変異確認の実施状況は申告された事実として扱い、未実施というだけでは指摘しない。実施行に結果がない場合、または未実施行に入れる欠陥・落ちる理由・未実施区分（範囲外／実施不能）がない場合は不足を指摘する。
- 維持価値を認めたテストについて、申告された欠陥で失敗するか実コードと照合する。commit・push・merge の可否を指摘の根拠にしない。
- 各指摘に正本の条件番号（例: 2-A-3、2-D-15、基準1〜4）を付ける。番号と意味は {{SHARED_SKILLS_PATH}}/gh-maestro-reviewer/test-quality/test-quality/criteria.md の正本に従う。

## 品質判定の確認

- **契約違反への感度**。価値を認めたテストが、入力に対する戻り値、保存後の状態、エラー、必要な副作用など、契約上のどの誤りを検出するか確認したか。
- **振る舞いを保つ変更への耐性**。内部構造や表現だけを変えても失敗するテストを見逃していないか。change-detector の指摘には、固定された実装詳細と、失敗する正当な変更を示したか。
- **修正案の適切さ**。定義、対応表、選択肢一覧、定数、内部文字列、文書文言をテストへコピーする修正案を勧めていないか。強化が必要な場合は、識別力のある入力と観測可能な結果・状態・エラー・必要な副作用を示したか。
- **振る舞いテストの誤指摘**。入力と観測可能な結果を使い、独立した契約を確かめるテストを change-detector と呼んでいないか。表や一覧や定数を含む、モックを使う、テストケースを反復するといった形式だけで判定していないか。
- **相互作用の契約**。モック呼び出し順・回数・引数だけを確かめるテストを確認したか。その相互作用自体が仕様で保証されている場合は、根拠なく不要と扱っていないか。
- **テストロジックと失敗の特定**。テスト内の条件分岐やループだけを理由に指摘せず、検証の正しさを読みにくくしている事実を確認したか。失敗時に壊れた振る舞いと入力を読み取れるかを確かめたか。

## 重点

- **前提としている世界の狭さ**。テストが成功するケースだけを想定していないか。拒否・遮断・縮退・回復を守る契約がある場合、その確認が必要か判断したか。
- **前提としている世界の形**。入力が実物や実物を作るコードと一致するか。実装者の想定だけから作られたfixtureに依存していないか。
- **偽りの緑**。モック都合で例外分岐がバイパスされていないか、アサーションが実質無効でないか、テストランナーをブロックしない副作用が残っていないか。
- **テスト自体の無傷性と隔離**。セットアップと後始末が対応しているか。一時ファイル、モック、タイマー、リスナー、環境変数などの汚染が漏れていないか。
- **テスト層の配置**。層が分かれている場合、関数単位で適切な層に置かれているか確認したか。
- **テストの振る舞い結合**。テスト名と検証内容のずれ、内部詳細への過度な依存を、実際に検出する欠陥と結び付けて確認したか。
- 描画された見た目を固定するテストは docs/adr/0033-do-not-pin-rendered-appearance-in-tests.md に従い、表示から分からない状態や関係の検証を削除対象にしていないか。

## 外部参照と指摘の制約

- diffが参照するテストヘルパーやfixtureは実ファイルを確認する。fixtureが実行時の状態や外部構造を模す場合は実物も確認する。
- 既存の同等テストがあるか確かめてから重複を指摘する。
- 個別具体例の機械的な網羅、好み、linterが扱う純粋なスタイル、実測のない性能推測、diff範囲外の一般的な設計を指摘しない。
- Test Quality レビューではテストを実行しない。docs/adr/0066-reviewer-runs-no-tests.md に従う。
