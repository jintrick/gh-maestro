# Test Quality — 事後確認表

## 重点

- **テストが前提としている世界の狭さ**:
  テストが「すべてが都合よく成功する世界」だけを前提にしていないか。
  守るべき性質はたいてい否定形である（壊れない・実行されない・漏洩しない・破損しない・ハングしない・受理されない）。
  肯定形のテストだけでは、否定形の性質（拒否・遮断・縮退・回復）は保証されない。
- **テストが前提としている世界の形**:
  テストが与える入力は、実物と同じ形をしているか。
  「都合よく成功する世界」が世界の狭さの問題であるのに対し、こちらは世界の形の問題である。
  異常系を足しても、前提そのものが実物とずれていれば、ずれた世界の中で網羅が増えるだけになる。
  入力がどこから来たかを問う。実装者が「実物はこうなっているはずだ」と書いた値か、
  実物または実物を作っているコードから取った値か。前者は実装者の認識であって事実ではない。
  実装とテストが同じ認識から作られている場合、その認識自体は誰にも検証されていない。
- **偽りの緑（緑であることが安全の根拠にならない場合）**:
  モックの都合で例外分岐がバイパスされている、アサーションが実質無効である、テストランナーをブロックしないバックグラウンド副作用（実プロセスの起動・未クリーンアップ状態）が存在するなど、テストがpassしていても安全が担保されていない状態を見抜く。
- **テスト自体の無傷性と隔離**:
  テストのセットアップ・後始末が正しく対になっているか。一時ファイル、モック、タイマー、リスナー、環境変数の汚染が漏れていないか。
- **テストの振る舞い結合**:
  テスト名と実際の検証内容の乖離、内部実装詳細への過度な依存、エッジケースの不足。

## 外部参照の裏取り

diffが参照する既存のテストヘルパーやfixtureは、実ファイルを読んで確認する。
既存の同等テストパターンがあるかを確認してからfindingを書く。

fixtureが実行時の状態や外部の構造を模している場合、模した対象の実物を読み、
形が一致しているかを確認する。対象がリポジトリ外にあっても読みに行く。

## 禁止

- 個別具体例の網羅を機械的に要求するだけのチェックリスト的指摘（本質的な性質の破綻に結びつかない指摘）
- 好みだけの指摘
- linterが自動で扱う純粋なスタイル指摘
- 実測のないパフォーマンス推測
- diff範囲外の一般的な設計指摘
