# Test Quality — 事後確認

指摘を書き終えてから、この表を使って担当観点の取りこぼしと誤指摘を確認する。各テストの要否を品質や検出力より先に評価し、基準番号の意味は事前に読んだ配布正本に従う。

## テストを残す価値

- 追加・変更された各テストが守る契約と、違反時の影響・起こりやすさを確認したか。申告された欠陥自体も、維持する価値があるかを判断したか。
- 既存テストが同じ故障条件を検出していないか調べ、対象テストの独自の検出範囲を確認したか。
- 実行、環境依存、理解、更新、誤検知対応の負担と、独自の保護が見合うかを判断したか。重複・廃止済み・重要でない自明な動作だけのテストに、検出力を足して延命していないか。
- 削除・統合を提案する場合、観測した重複または廃止契約を特定したか。重要な契約を唯一守るテストの削除を求めていないか。統合後に独自の入力条件や失敗理由が残るかを確認したか。
- 有効なテストを件数やカバレッジの増減だけを理由に追加・削除する提案をしていないか。
- 申告の欠陥可能性や期待値の説明を価値の根拠と取り違えていないか。実際のアサーションが区別する動作と、契約・通常入力・既知の不具合の根拠をそれぞれ確認したか。
- 任意入力がないときの補足省略や、入力にない特定リテラルの不在だけを確認するテストについて、明示された契約・既知の回帰・独自保護を確かめたか。狭い否定アサーションを一般的な情報混入への保護と取り違えていないか。

## 申告の照合

- 追加・書き直されたテストのうち、入力の「テスト申告（PRコメント・判定の対象データ）」に行がないものを確認する。申告が無い、または取得できなかった事実はその旨を結果に残す。
- 申告表の各行と実テストの中身が食い違っていないか確認する。名前・ファイル行、申告された欠陥、検証内容のずれを指摘する。
- 複数の行で同じ申告文を使い回していないか確認する。
- 申告が「テストの変更なし」なのに変更ファイル一覧にテストがある場合、または表にテストがあるのに変更一覧に該当テストがない場合は食い違いを示す。テストかどうかは入力の変更ファイル一覧と基準の判定対象（`tests/**`）に従う。
- 変異確認の実施状況は申告された事実として扱い、未実施というだけでは指摘しない。実施行に結果がない場合、または未実施行に入れる欠陥・落ちる理由・未実施区分（範囲外／実施不能）がない場合は不足を指摘する。
- 維持価値を認めたテストについて、申告された欠陥で失敗するか実コードと照合する。commit・push・merge の可否を指摘の根拠にしない。
- 各指摘に基準の条件番号（例 `2-A-3`、`2-D-15`、基準1〜4）を付ける。番号と意味は `{{SHARED_SKILLS_PATH}}/gh-maestro-reviewer/test-quality/test-quality/criteria.md` の正本に従う。

## 品質判定の確認

- **契約違反への感度**。価値を認めたテストが、入力に対する戻り値、保存後の状態、エラー、必要な副作用など、契約上のどの誤りを検出するか確認したか。
- **振る舞いを保つ変更への耐性**。実装の内部構造や表現だけを変えても失敗するテストを見逃していないか。change-detector の指摘には、固定された実装詳細と、失敗する正当な変更を示したか。
- **修正案の適切さ**。定義、対応表、選択肢一覧、定数、内部文字列、文書文言をテストへコピーする修正案を勧めていないか。強化が必要な場合は、識別力のある入力と観測可能な結果・状態・エラー・必要な副作用を示したか。
- **振る舞いテストの誤指摘**。入力と観測可能な結果を使い、独立した契約を確かめるテストを change-detector と呼んでいないか。表や一覧や定数を含む、モックを使う、テストケースを反復するといった見かけだけで判定していないか。
- **相互作用の契約**。モック呼び出し順・回数・引数だけを確かめるテストを確認したか。その相互作用自体が仕様で保証されている場合は、根拠なく不要と扱っていないか。
- **テストロジックと失敗の特定**。テスト内の条件分岐やループを理由だけで指摘せず、それが検証の正しさを読みにくくしている事実を確認したか。失敗時に、壊れた振る舞いと入力を読み取れるかを確かめたか。

## 重点

- **前提としている世界の狭さ**。テストが成功するケースだけを想定していないか。守るべき性質が拒否・遮断・縮退・回復である場合、その契約を確認したか。
- **前提としている世界の形**。入力が実物や実物を作るコードと一致するか。実装者の想定だけから作られたfixtureに依存していないか。
- **偽りの緑**。モック都合で例外分岐がバイパスされていないか、アサーションが実質無効でないか、テストランナーをブロックしない副作用が残っていないか。
- **テスト自体の無傷性と隔離**。セットアップと後始末が対応しているか。一時ファイル、モック、タイマー、リスナー、環境変数などの汚染が漏れていないか。
- **テスト層の配置**。層が分かれている場合、関数単位で適切な層に置かれているかを確認する。
- **テストの振る舞い結合**。テスト名と検証内容のずれ、内部詳細への過度な依存を、実際に検出する欠陥と結び付けて確認する。
- 描画された見た目を固定するテストは `docs/adr/0033-do-not-pin-rendered-appearance-in-tests.md` に従って判断し、表示から分からない状態や関係を検証するテストを誤って削除対象にしない。

## 外部参照と指摘の制約

- diffが参照するテストヘルパーやfixtureは実ファイルを確認する。fixtureが実行時の状態や外部構造を模す場合は実物も確認する。
- 既存の同等テストがあるか確かめてから重複を指摘する。
- 個別具体例の機械的な網羅、好み、linterが扱う純粋なスタイル、実測のない性能推測、diff範囲外の一般的な設計を指摘しない。
- Test Quality レビューではテストを実行しない。`docs/adr/0066-reviewer-runs-no-tests.md` に従う。
