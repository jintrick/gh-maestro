# Maintainability / Design Quality

目的: 差分の設計が、レビュー対象プロジェクト自身の設計原則と適切なデザインパターンに沿うかを判定する。また、差分で足された処理が、リポジトリの既存の処理・共有部品と重複していないかを確かめる。手戻りの大きい作りを、マージ前に指摘する。

## 原則の読み取り（対象プロジェクトから）

設計原則は、レビュー対象プロジェクトのファイルからだけ読む。PR の head 側は PR 自身が書き換えうるため使わない。読む対象は PR の base commit に固定する。追跡ブランチ（`origin/<base>`）は使わない。レビュー用worktreeは PR head の専用refしか取得しないため、追跡ブランチは古いか存在しない。

1. `gh pr view <PR> --repo <REPO> --json baseRefOid --jq .baseRefOid` で base commit（`BASE_OID`）を得る。失敗したら取得失敗とする。
2. `git fetch --no-tags origin <BASE_OID>` で base commit を取得する。失敗したら取得失敗とする。
3. `AGENTS.md` を `BASE_OID` に対して読む:
   - `git ls-tree <BASE_OID> -- AGENTS.md` で存在を確かめ、出力があれば `git show <BASE_OID>:AGENTS.md` で読む（空なら存在しない）。
   - `git ls-tree` または `git show` 自体が失敗した場合は、取得失敗とする。
4. `.claude/rules/` から PR の変更ファイルに関係するルールだけを `BASE_OID` に対して特定し、読む:
   - プロンプトの `### 変更ファイル一覧` にある各ファイルパス（`(情報なし)` の場合は `git diff --name-only <BASE_OID>...HEAD` で取得）を渡し、`node "{{SCRIPTS_PATH}}/find-matching-rules.js" --ref <BASE_OID> <変更ファイル...>` を実行する（`git diff` が失敗したら取得失敗とする）。
   - `find-matching-rules.js` が非ゼロ終了した場合は取得失敗とする（「当てはまるルールなし」として続けない）。
   - 終了コード `0` で出力が空のときは、`.claude/rules/` が無いか、変更ファイルに `paths:` が当てはまるルールが 0 件である（`paths:` を持たないルールも読まない）。
   - 出力された各パスだけを `git show <BASE_OID>:<path>` で読む。`git show` が失敗した場合は取得失敗とする。
5. 読み取った `AGENTS.md`（あれば）と一致した `.claude/rules/` から、設計に関係する原則（責務の分け方、配置、共有部品の使い方、依存の向き）だけを抜き出し、原則ごとに出典（ファイルパスと見出しまたは行）を控える。

取得失敗と当てはまるルール 0 件の扱い:
- いずれかの取得・列挙・照合・読取が失敗したときは、「原則なし」として続けてはならない。この葉では設計評価と指摘を行わず、取得失敗の理由（どの取得が失敗したか）を結果に残す。
- 取得は成功したが当てはまる `.claude/rules/` が 0 件のとき、および `AGENTS.md` が存在しないときは、取得失敗とは区別してその事実を結果に残す。原則を推測で補ってはならない。この場合は、`AGENTS.md`（存在する場合）とデザインパターンおよび重複の探索で評価を続ける。

レビュー担当の記憶や一般論を、対象プロジェクトの原則として扱ってはならない。

## 重複の探索（差分の外も見る）

差分で足された関数・処理ごとに、同じ目的の既存の処理や共有部品が、リポジトリのほかの場所にないかを探す。

- 差分の処理が何を判定・変換・保存するかを1行で書く。
- `git grep` で、その目的を表す関数名・語・同じ外部コマンドの呼び出しを探す。
- 既存の共有部品が見つかったら、その定義と差分の処理を読み比べる。

目的が同じ既存部品だけを重複として扱う。語が偶然一致しただけなら指摘しない。

## 設計の評価

- 対象プロジェクトの原則に反する箇所（責務の混在、依存の向き、配置の誤り）。
- 既存の作りに反するパターンの選択（同じ分岐の繰り返し、既存の抽象を迂回した直接実装など）。適切なパターンと、その根拠を示す。
- 指摘は差分の処理に限る。差分と無関係な設計一般論は挙げない。

## 根拠（必須）

指摘ごとに、次のどちらかを付ける。根拠を示せない指摘は出さない。

- 原則違反: 反している原則の出典（ファイルパスと見出しまたは行）と、要点の引用。
- 重複: 既存の処理・共有部品の `ファイル:行` と、差分側の `ファイル:行`。

## 禁止

- 好みだけの指摘、linterが自動で扱う指摘
- 原則の出典が無いのに「設計原則違反」と書くこと
- 差分と無関係な設計一般論
- 実測のないパフォーマンス推測
