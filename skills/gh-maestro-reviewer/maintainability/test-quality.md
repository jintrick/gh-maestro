# Maintainability / Test Quality

目的: 受け入れ条件をテストが実際に保証しているかを判定する。テスト自体が将来の事故の温床になっていないかを探す。

## 確認順序

1. この変更が守ろうとしている性質を1文で言い切る。テストが、**その性質が破られる状況を実際に作っているか**を確認する。
2. **テストが緑になる理由を確かめる。** 検査したい箇所を本当に踏んでいるか。モックやスタブで固定した結果、その分岐が素通りしていないか。
3. テストが固定しているのは**あるべき振る舞い**か、それとも**現在の実装**か。

## 重点

- 守るべき性質はたいてい否定形である（壊れないこと・実行されないこと・受理されないこと）。
  肯定形のテストだけでは、否定形の性質は保証されない
- 外部（コマンド・API・ファイル・別プロセス）が期待どおりに応えない場合
- 緑であることが安全の根拠にならない場合がある
- テスト名、テストの実装詳細依存、エッジケース不足
- テストのクリーンアップ漏れ: 追加した`beforeEach`/`afterEach`、一時ファイル、
  モック、タイマー、リスナーの後始末忘れ
- テストが常にpassする(assertionが実質無効な)偽陽性

## 外部参照の裏取り

diffが参照する既存のテストヘルパーやfixtureは、判定前に実ファイルを読んで確認する。
既存の同等テストパターンがあるかを確認してからfindingを書く。

## 禁止

- **スコープ限定なしの全件テスト実行（`npm test` 等）および全体ビルド（`npm run build` 等）は禁止。** diffで変更された特定のテストファイルのみを対象にしたピンポイント実行（例: `node --test tests/<file>.test.js`）は許容する
- 好みだけの指摘
- linterが自動で扱う純粋なスタイル指摘
- 実測のないパフォーマンス推測
- diff範囲外の一般的な設計指摘
