description: 保留Issue（gh-maestro-pendingラベル）に溜まったコメントをトリアージし、切り出し済み・統合済みで重複した記録を削除する。オーケストレーターが自分の判断で実行する（ワーカー起動不要）。
---

保留Issueは push/pop 型のスタックである。切り出し・統合・直接修正のいずれかで対応が決まった項目は、その時点で SSOT（正本）が切り出し先Issue／コミット／PRへ移る。保留Issue側に「切り出し済み」「解決済み」等のマーカーを残す運用は廃止した——正本が移った後もマーカーを残すと、どちらが正本か判断するために両方を突き合わせる手間が発生し、実際に混乱の原因になった（2026-08-17）。対応が決まった項目は、マーカーを経由せず保留Issueから即座に削除（pop）する。このスキルは、この運用に切り替わる前に作られた「切り出し済み／統合済みマーカーとその重複記録」の残骸を一度きり整理するためのものである。今後の切り出しは `gh-maestro-orchestrator` SKILL.md の「保留Issueへの追記」手順（削除のみ・マーカーを作らない）に従う。

このスキルはオーケストレーター自身が実行する。GitHub Issueコメントの読み取り・分類はソースコード分析ではなく、オーケストレーターに許可された「PR/Issue情報の取得」の範囲内である。ワーカーを起動する必要はない。

## 前提

- `REPO`・`WORKSPACE` はセッション変数から取得する
- 保留Issueは `gh-maestro-pending` ラベルでリポジトリ全体に常に1件のみ存在する（PR番号非依存）

```sh
PENDING_ISSUE=$(gh issue list --repo $REPO --label gh-maestro-pending --state open --json number -q '.[0].number')
```

## 手順

### 1. 全コメントを取得する

REST APIで取得する（`databaseId`が直接手に入るため、削除時にGraphQLでの追加解決が不要）。

```sh
gh api "repos/$REPO/issues/$PENDING_ISSUE/comments" --paginate \
  --jq '.[] | "\(.id)|||\(.body)"'
```

### 2. コメントを分類する

各コメントを以下のいずれかに分類する。判断はコメント本文の突き合わせのみで行い、対象ファイルのソースコードを読みに行かない（読む必要が生じた場合はexplorerに委譲する）。

| 分類 | 判定基準 | 扱い |
|---|---|---|
| **対応済み（旧マーカー／重複）** | `[切り出し済み → #N]` / `[統合済み → #N]` / `[解決済み...]` / `[対応済み...]` 等のマーカーで始まる。または `[保留]` コメントの内容が、そうしたマーカーコメントの本文中に同一ファイル・同一指摘として明記されている | 削除候補（マーカー自体もその元になった `[保留]` コメントも、正本は切り出し先／コミット側に移っているため保留Issue側に残す意味がない） |
| **決定記録** | `[保留]` だが「対応不要」「設計上のトレードオフとして記録」等、今後もアクションを起こさない前提が明記されている | 保持（削除しない） |
| **未解決の設計判断待ち** | `[保留]` だが人間の意思決定がまだ必要と明記されている（例: 警告かエラー停止か等） | 保持（削除しない） |
| **未切り出しの有効な指摘** | `[保留]` で、上記いずれにも該当せず、まだどの切り出しIssueにも統合されていない | 保持（将来の切り出し候補） |

「対応済み（旧マーカー／重複）」以外は削除しない。判断に迷うコメントは削除候補に含めず保持側に倒す。マーカーが指す切り出し先Issueの状態（Open/Closed）は削除可否に影響しない——Closedなら実装済み、Openでも既にそちらへ切り出し済み（保留Issueからは離脱済み）という点は変わらないため、いずれもマーカー自体は削除候補である。

### 3. 削除候補を人間に提示し、明示的な確認を取る

GitHubコメントの削除は取り消せない外部システムへの書き込みである。**削除候補リストを提示し、ユーザーの明示的な承認を得るまで絶対に削除を実行しない。** 一括削除の実行そのものが「External System Writes」として自動承認の対象外になる場合があるため、コマンド実行時に改めて確認を求められたら、ユーザーに再度明示の同意を得ること。

提示フォーマット:

```
削除候補（N件・理由は重複統合済み）:
- <内容の要約>（→ #<切り出し先>に統合済み）
...

保持（M件）:
- <カテゴリ>: <内容の要約>
...

この方針で削除してよいですか？
```

### 4. 承認後、削除を実行する

```sh
for id in <databaseId1> <databaseId2> ...; do
  gh api -X DELETE "repos/$REPO/issues/comments/$id"
done
```

### 5. 結果を報告する

```sh
gh api "repos/$REPO/issues/$PENDING_ISSUE/comments" --paginate --jq 'length'
```

削除後の残存件数と、保持したコメントの内訳（監査記録／決定記録／設計判断待ち／未切り出し）を簡潔に報告する。
